## 一、三层到底谁负责什么

这张表是我写完代码才想清楚的，比任何架构图都实用：

| 层 | 负责 | **不负责** |
| --- | --- | --- |
| Host 宿主 | 模型、对话循环、UI、决定要不要调工具 | 协议细节、工具实现 |
| Client 协议客户端 | 与**一个** Server 的一对一连接、握手、帧收发与匹配、能力缓存 | 选哪个工具、工具业务逻辑 |
| Server 工具服务 | 工具实现、资源读取、提示词模板、自己的能力声明 | 模型、对话历史、用户是谁 |

关键在于「不负责」那一列。三个最常见的架构错误都来自越界：

- Server 里存对话历史 → 换个 Host 就全丢了，而且同一个 server 被两个 session 调用会串台。
- Client 决定调哪个工具 → 那就不是 Client 了，那是 Host 的模型在干的事。
- Host 直接拼 JSON-RPC 帧 → 每接一个 server 重写一遍传输层，MCP 的意义就没了。

自检里专门断言了「Client 的 does_not_own 里必须有『选哪个工具』」这种条目 ——
听起来像在测文档，其实是把架构约束钉成可回归的断言。

## 二、stdio 上唯一真正的难点：帧边界

TCP 和管道都只保证字节顺序，**不保证消息边界**。所以 stdio 传输必须自己定一个分隔符，
MCP 定的是 `\n`。于是有了这条硬规则：

> **帧里不能有裸换行。**

`json.dumps` 默认就是一行，没问题。但只要你顺手加了 `indent=2`：

```python
json.dumps(frame, indent=2)
```

实测：`tools/list` 帧从 **47 字节涨到 60 字节**，里面有 **5 个换行**。
喂进分帧器，第一个换行切在 `{` 后面，`json.loads("{")` 直接抛：

```
分帧成功但 JSON 非法：Expecting property name enclosed in double quotes；
原始行=b'{'
```

注意这条报错的措辞 —— 「分帧成功但 JSON 非法」。这个区分是有意的：
分帧器只负责找边界，它找到了一个边界（第一个 `\n`），只是边界之间的东西不是合法 JSON。
**把这两类错误分开报，是排查的第一步。**

## 三、增量分帧：一个 buffer 加一个 while

```python
buffer.extend(chunk)
while (idx := buffer.find(b"\n")) >= 0:
    line = buffer[:idx]; del buffer[:idx + 1]
    if line.strip(): frames.append(json.loads(line))
```

三件事必须做对：

1. **残留要留着**。返回 `[]` 不代表出错，代表「还没凑齐」。自检里断言了：喂半帧返回空，
   且 `pending` 长度等于喂进去的长度。
2. **一次可能切出多帧**。喂两帧连在一起，必须返回 2 个。漏了这点，高频调用时会莫名丢帧。
3. **空行跳过**。`\n\n\n` 不是三个空帧，是填充。把它当帧会立刻 JSON 解析失败。

实测按 7 字节切片喂一个 47 字节的帧：走了 **7 步**，中间最多残留 6 字节，最后切出 1 帧。

## 四、EOF：那个没人写的 else 分支

```python
chunk = reader.read()
if not chunk:
    if reader.closed:
        return "eof"          # 客户端走了，我也走
    return "would_block"      # 暂时没数据，别退
```

不写这段的后果：客户端断开后，服务端进程挂在那里等一个再也不会来的字节。
宿主每重启一次多一个僵尸，跑一天能攒出几百个。

还有一个更隐蔽的分支：**半帧 + EOF**。对面写了一半就断了。
这不是正常结束，是丢帧。所以要单独报 `eof_with_partial_frame` 并把残留字节打出来 ——
自检中断言了残留里能看到 `"met`（我故意只写了 `{"jsonrpc":"2.0","id":9,"met`）。

## 五、HTTP：分帧问题消失，会话问题上桌

换成 HTTP 之后，每条消息自带边界（`Content-Length`），分帧器可以删掉了。
但两件事要自己补：

**第一，连接身份。** stdio 上「一条连接」天然等于「一个进程 = 一份状态」。
HTTP 上每个请求都可能是新连接，服务器只能靠 `Mcp-Session-Id` 头把请求串回同一个逻辑会话。

第一步 `initialize` 不需要 session（还没有），服务器在**响应头**里发一个；
之后每个请求都必须带着它。不带 —— 实测返回 **400**。
症状很典型：每次请求都重新握手，工具列表时有时无，且看不出规律。

**第二，主动通知往哪推。** HTTP 是请求-响应，服务端想主动说「工具列表变了」没有出口。
这就是 Streamable HTTP 里那一半 SSE 的由来：一个长连接专门承接服务端推送。
stdio 没这个问题 —— 管道本来就是双向的。

## 六、字节成本：反直觉的那一面

第一反应是「HTTP 更轻，因为它没有长连接开销」。实测反了：

| | initialize | notifications/initialized | tools/list | 合计 |
| --- | --- | --- | --- | --- |
| stdio（一行一帧） | 89 | 55 | 47 | **191** |
| HTTP（头 + 体） | 294 | 260 | 252 | **806** |

**4.22 倍，多付 615 字节。** 因为每一帧都要带上请求行、`Host`、`Content-Type`、
`Content-Length`、`Mcp-Session-Id`，再加上响应头 —— 而 body 只有几十字节。

所以「stdio 适合本地工具」不是审美偏好，是算术：本地进程之间，一个 30 字节的头都嫌贵。
反过来说，HTTP 换来的是多客户端、可鉴权、能穿防火墙 —— 到了多用户场景，这 4 倍完全值得付。

## 七、一个 FastAPI 的坑（顺手记下）

`def rpc(payload, response: Response)` 里设 `response.headers[...]`，
然后 `return JSONResponse(...)` —— **你设的头会静默消失**。
因为注入的 `Response` 对象只在「返回 dict 让 FastAPI 自己构造响应」时被使用，
你直接返回一个 Response，注入的那个就被丢了。

正确做法二选一：在**返回的那个对象上**设头，或者 `return dict`。
我第一版就是这么挂的，症状是 `Mcp-Session-Id` 为 `None`，然后下游 header 写入抛
`TypeError: Header value must be str or bytes, not NoneType`。

## 一句话总结

**协议定义「说什么」，传输决定「怎么说、以及说漏了怎么办」——
后者才是线上事故的高发区。**

## 面试追问

**Q：为什么 MCP 本地传输选 stdio 而不是 Unix socket 或本地 HTTP？**
A：三个原因。一是**零配置**：stdio 不需要端口、不需要文件锁、不需要处理端口占用，
子进程一拉起来就能说话，而 Unix socket 要协商一个路径、还要管权限和残留文件。
二是**生命周期天然绑定**：父进程退出，管道关闭，子进程读到 EOF 自然退出 —— socket 不会，
你得额外做进程管理。三是**权限继承**：stdio 的权限就是启动它的用户的权限，
不需要另设一套鉴权；本地 HTTP 反而要防「同一台机器上的其他用户也能访问这个端口」。
代价是只能一对一，且没法跨机器。

**Q：stdio 传输下，怎么知道对方发完了一帧？**
A：靠换行。MCP 规定 stdio 上每条消息是一行 JSON，`\n` 就是边界。
这也意味着**帧内不能有裸换行**，所以序列化必须用紧凑模式，不能 `indent`。
解析侧必须做增量缓冲：一次 `read()` 可能拿到半帧（留着等），也可能拿到多帧（全切出来）。

**Q：HTTP 传输下服务端怎么主动通知客户端？**
A：靠一条反向的 SSE 长连接。客户端在 `initialize` 之后维持一个 GET 的流，
服务端把通知作为 SSE event 推下去。这正是 Streamable HTTP 名字的来历 ——
请求走 POST，推送走 SSE，同一份 session 上两条通道。
没有这条通道，`listChanged` 这类能力根本没法实现（声明了也发不出来）。

**Q：为什么 stdio 的服务器必须处理 EOF？**
A：因为管道关闭后，`read()` 会**立即**返回 0 而不是阻塞 —— 但它不会帮你退出进程。
如果不处理，你会得到一个永远在空转、或者在阻塞等待的进程。
宿主（Claude Desktop / Cursor）每次重启都拉起新的一批，旧的没人收，
一天下来能攒出几百个僵尸进程，把 PID 耗尽。所以 EOF 必须映射成「清理 + 退出」。
