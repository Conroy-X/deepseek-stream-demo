## 5 个核心认知

| 概念 | 一句话解释 | 怎么验证 |
| --- | --- | --- |
| **Token** | 最小处理单位，约「中文 1~2 字 / 英文 4 字符」 | `--offline` 实验 1 打印对照表 |
| **Context Window** | 一次请求「输入 + 输出」的总 token 上限 | 实验 3 看输入逐轮累加 |
| **Prompt** | System（规则）+ User（输入） | 实验 2/4 改一句就看得出差别 |
| **Temperature** | 随机性，0 最确定、2 最发散 | 实验 2 同一问题跑 3 次 |
| **API 调用** | 一切按 token 计费 | 实验 3/4 每次打印用量与费用 |

**最关键的一条**：LLM 本身**没有记忆**。所谓「对话」，
是应用层每次把完整历史重新发一遍。这直接导致 Unit 10 的上下文管理问题。

## 四个实验各自证明什么

### 实验 1 · Token 不等于字数
中文和英文的 token 密度完全不同，**按字数估成本会算错**。
标点、空格、代码符号都算 token。
Prompt 模板里的固定文字（角色设定、示例）**每次调用都在重复付费**。

### 实验 2 · Temperature 的边界
`0.0` 最稳定，但**不保证逐字相同**（浮点累加顺序、批处理、MoE 路由都会带来微差）。
- 事实抽取/分类/结构化输出 → `0~0.3`
- 创意写作 → `0.8~1.2`
- `temperature` 和 `top_p` 别同时乱调

### 实验 3 · Context 的增长曲线
输入 token 逐轮累加，总成本接近**平方级**。
轮次多了以后变贵、变慢，还可能在中间位置丢失信息（lost in the middle）。

### 实验 4 · max_tokens 与 stream
`finish_reason='length'` 说明**被截断**，不是答完了。
`stream=True` 让文字逐字出现，首字延迟（TTFT）大幅下降。

## 实测：推理 token 占比很夸张

`deepseek-flash` 默认开思考模式，实测「只回答两个字：成功」也要 31 个 output token，
其中 **29 个是推理（94%）**。

**含义**：设 `max_tokens` 时不能只按「预期回答长度」估，
要把推理 token 也算进去，否则回答会被悄悄截断。
