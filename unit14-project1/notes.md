## 核心：流式 + 落库的四个决策

### 决策 1：用户消息在调用模型**之前**就入库

```python
session.add(user_msg)
session.commit()          # ← 先提交
messages = build_context(...)
async for event in client.chat_stream(...): ...
```

为什么不能等模型回复完一起写？
- 模型报错 / 被限流 / 用户关页面 → 这条消息就凭空消失了
- 用户刷新页面发现"我刚说的话没了"，会以为是前端 bug
- 排查线上问题时，你甚至不知道用户问过什么

**先留痕，再生成。** 这是所有"请求-响应"型业务（含下单、支付）的通用原则。

### 决策 2：助手消息在流结束后写入，哪怕只有半句

```python
if await request.is_disconnected():
    break          # 但 parts 里已经收到的内容不丢弃
...
content = "".join(parts)
if content:
    session.add(Message(role="assistant", content=content, ...))
```

用户中途关页面时，他**已经看见了那半句话**。如果不存，下次进来历史是断裂的：
用户记得自己看到过回答，但历史里只有问题。

所以断线也要保存已生成部分，并在 `saved` 事件里标 `interrupted: true`，让前端能提示"已中断"。

### 决策 3：空的助手消息不写

```python
if content:      # ← 这个判断很关键
    session.add(...)
```

第一秒就报错的情况下 `parts` 是空的。写一条空消息进去，会让历史里出现一个空气泡，
而且下一次 `build_context` 会把 `{"role": "assistant", "content": ""}` 喂给模型 ——
部分模型会直接返回 400（assistant 内容不能为空）。

### 决策 4：流式生成里必须**新开** Session

这是本例最隐蔽的坑：

```python
async def gen():
    ...
    with Session(store.engine) as s2:   # ← 不能用请求级的 session
        s2.add(Message(...))
        s2.commit()
```

原因：`StreamingResponse` 的生成器是在**响应头已经返回给客户端之后**才被迭代的。
而 FastAPI 的依赖（`Depends(store.get_session)`）的 `with` 块在**响应返回的那一刻**就退出了，
session 已经关闭。

在生成器里用那个 session，会拿到 `This session is closed` 或者更诡异的
"连接已被归还到池里，同时被另一个请求借走了"。

**记住：流式接口里，超出依赖作用域的数据库操作必须自己开 session。**

## 上下文裁剪

```python
MAX_CONTEXT_MESSAGES = 20
```

不做裁剪的话，问题在第 30 轮左右爆发，而且有三个症状同时出现：

1. **成本线性上涨**：每轮都把全部历史重新发一遍，第 50 轮单轮 token 是第 1 轮的 50 倍
2. **撞上下文上限**：直接 400，用户以为服务挂了
3. **变慢**：首 token 延迟随历史长度增长

裁剪策略的选择（Unit 10 讲过三种）：
- 滑动窗口（本单元采用）：简单、可预测、成本有上界，但会"忘掉"早期信息
- 摘要压缩：保留长期记忆，但要多一次 LLM 调用（还要为摘要付钱）
- 语义检索：历史里捞相关的几条，最像人，但要先有 embedding（这就是阶段二要做的 RAG）

排序用 `(created_at DESC, id DESC)` 双字段而不是只按时间：同一秒内写入的两条消息
`created_at` 可能完全相同，只按时间排会偶发顺序错乱（用户消息跑到助手回复后面）。

## 一句话总结

流式对话的难点不在流，而在"**流是一种持续进行的状态**"——它迫使你重新想清楚
哪些数据要提前落、哪些可以延后、断线时算哪一半成功。
把这些时序问题想清楚，RAG 和 Agent 的流式只是换个内容来源而已。

## 面试追问

1. **「用户中途关掉页面，这次回答还算数吗？」**
   → 算。已生成部分会入库并标记中断。理由：用户已经看见了，不存会导致历史断裂；
   而且从成本角度，这部分 token 已经付过钱了，丢掉纯亏。

2. **「为什么用户消息要先入库？」**
   → 保证"用户说过的话不丢"。模型可能失败，但请求本身是既成事实。
   一旦写进库，排查问题、重试、展示都有依据。

3. **「长对话怎么控制成本？」**
   → 三层：滑动窗口截断历史（本单元）→ 摘要压缩保长期记忆 → 语义检索只取相关片段。
   再加 `max_tokens` 限制单次输出上限，以及按用户记账防超支。

4. **「流式接口里能不能用请求级的数据库 session？」**
   → 不能。依赖的 `with` 块在响应头返回时就退出了，生成器迭代时 session 已关闭。
   必须在生成器内部自己开 session。

5. **「为什么不用 WebSocket？」**
   → 这个场景是"一问一答、单向推送"，SSE 足够且更简单：走 HTTP、天然支持断线重连
   （浏览器 EventSource）、不用维护连接状态、经过代理更友好。
   WebSocket 适合双向实时（协同编辑、游戏）；要双向又要简单，可以先 SSE + POST 组合。
