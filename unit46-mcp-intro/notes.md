# Unit 46 笔记 · MCP 是什么

> 讲 MCP 最省事的说法是「AI 的 USB-C」。但 USB-C 不会因为你插上就自动传数据 ——
> 真正要记住的是：**它是一层 JSON-RPC 2.0，加一次能力协商。**

## 本次做了什么

- 手写 `protocol.py`：帧构造/校验、能力协商、`MiniServer` 状态机、四步握手脚本。
- 写 `main.py`：6 个接口 + 76 条离线自检（0 失败）。
- 写 `static/index.html`：协议解剖台（生命周期四步、发帧、能力表、服务器日志）。
- **没有装 `mcp` SDK**，这是故意的 —— 见下面第一节。

## 一、为什么这一章不用 SDK

用 SDK 写 server 只要十行：

```python
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("demo")
@mcp.tool()
def add(a: int, b: int) -> int: return a + b
```

跑得起来，但你答不出这些问题：握手报文长什么样？能力协商谈了什么？
没握手调工具返回哪个码？工具抛异常在报文里是什么形状？

于是出问题时只有两条路：读源码，或者瞎试。所以本单元把协议**手写一遍**，
第 49 章再换回 SDK —— 那时候你看到装饰器，脑子里知道它背后在发什么。

## 二、M+N 与 M×N

MCP 的动机可以说得很实在：

```
没有协议：  M 个宿主 × N 个工具 = M×N 个适配器
有协议：    M 个宿主 + N 个工具 = M+N 个实现
```

数字不好看的部分在于：**协议只统一了「怎么说话」，没统一「说什么」**。
工具语义（参数含义、返回结构）仍然要靠 `description` 和 `inputSchema` 表达，
这直接决定了模型能不能用对 —— 这就是 Unit 32 讲 Schema 的原因。

## 三、三种帧，少一种都不行

| 类型 | 有 id | 服务器回不回 | 典型用途 |
| --- | --- | --- | --- |
| request | ✅ | 回 result 或 error | `tools/list`、`tools/call` |
| response | ✅ | —— | 回给某个请求 |
| notification | ❌ | **不回** | `notifications/initialized`、`tools/list_changed` |

自检里 `"1"` vs `1` 那条断言值得单独说：`match_response` 要求 **id 的类型也一致**。
见过 `str(id)` 的实现，客户端永远匹配不上，症状是「一直等、最后超时」，日志里一点错都没有。

## 四、生命周期：两个状态，一条硬规则

```
未初始化 ──initialize──> 已协商 ──notifications/initialized──> 就绪
```

硬规则：**未就绪时，除 `initialize` 和 `ping` 外的请求一律 `-32002`。**

为什么 `ping` 例外：探活要在任何时候都能用，否则「服务器没起来」和「服务器起来了但没握手」
这两种故障你分不开。

为什么握手要拆两步（请求 + 通知）而不是一步：客户端收到 `initialize` 的响应后，
可能还要做本地准备（注册回调、挂载能力表、初始化工具缓存）。第二步是它说「我准备好了」。

## 五、能力表：声明的边界就是能力的边界

```python
server_capabilities(tools=True, resources=False, prompts=False)
→ {"tools": {"listChanged": False}}
```

实测：把 `resources` 关掉之后，`resources/list` 返回的不是「拒绝」，而是 **`-32601 Method not found`**。

这个区别很关键：`-32601` 说的是「这里没有这个功能」，不是「你不能用」。
客户端据此决定 UI 上要不要显示「资源」面板 —— 而不是先试一次再捕获错误。

`listChanged: true` 是**承诺**：声明了就必须在列表变化时主动发通知。不发，客户端会一直等。

## 六、工具失败 ≠ 协议失败

这是全章最重要的一条，也是最多人写错的一条。

```json
{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"工具执行失败：ValueError: a 和 b 必须是数字"}],"isError":true}}
```

对比错误写法：

```json
{"jsonrpc":"2.0","id":3,"error":{"code":-32603,"message":"ValueError"}}
```

后者的后果：客户端把这次调用当成「服务器坏了」，抛异常、重试、或者直接 500。
**模型永远看不到「a 和 b 必须是数字」这句话**，于是它不知道自己错在哪，也就没法改。

前者把失败变成了一条**内容**，模型能读到、能据此修正参数。这和 Unit 31 里
「工具报错也变成可读回答」是同一条原则，只是发生在协议层。

## 七、错误码只加了两个

JSON-RPC 2.0 原有：`-32700` 解析失败、`-32600` 帧非法、`-32601` 方法不存在、
`-32602` 参数非法、`-32603` 内部错误。
MCP 额外加了 `-32002`（未初始化）和 `-32001`（请求被取消）。

实测这几条都验过：非法帧 `-32600`、未知方法 `-32601`、未知工具 `-32602`、未握手 `-32002`。
分清楚它们的意义在于 —— 你看到哪个码，就知道该改代码的哪一层：传输、协议、还是业务。

## 完成标准对照

| 标准 | 达成情况 |
| --- | --- |
| 能写四种帧 | `make_request / make_result / make_notification / make_error`，自检逐条验 |
| 能做版本协商 | `negotiate()` 只接受支持列表里的版本，否则 `-32602` 并列出支持项 |
| 能解释生命周期 | `MiniServer` 两状态机，未握手 `-32002`，`ping` 例外 |
| 能分清两类失败 | 工具异常 → `result.isError`；协议错 → `error` 帧 |
| 离线可自检 | 76 条断言，0 失败，无 SDK、无网络 |

## 一句话总结

**MCP 的复杂度不在协议，而在「哪些东西属于协议、哪些属于工具设计」这条分界线上。**

## 面试追问

**Q：MCP 和 OpenAPI 有什么区别？**
A：OpenAPI 描述的是「HTTP 接口长什么样」，MCP 描述的是「一个进程能给 AI 提供什么能力，以及怎么被发现」。
三个实际差别：一是 MCP 有**运行时发现**（`tools/list` 动态拿清单），OpenAPI 通常是构建期生成的静态文档；
二是 MCP 有**双向能力**（服务器可以反过来请求客户端的 `sampling` / `roots`），OpenAPI 是单向的；
三是 MCP 面向的是「模型在对话中自己选工具」，所以 schema 的 `description` 是给模型读的提示词，而 OpenAPI 的文档是给人读的。

**Q：为什么工具失败不用 error 帧？**
A：因为 `error` 在 JSON-RPC 里表示「这次调用本身有问题」（方法不存在、参数结构非法、服务器崩了），
客户端会按协议异常处理 —— 抛错、重试、或者断开。而「查不到这个订单」是**业务结果**，
模型需要读到这句话才能换策略。所以 MCP 用 `result` + `isError: true`：调用成功、内容表示失败。
一句话：协议层失败和业务层失败必须分开，否则模型被蒙在鼓里。

**Q：stdio 传输下，服务器怎么知道客户端断开了？**
A：stdin 读到 EOF。这是 stdio 最大的坑：服务器进程不会自动退出，它会挂在那里等一个再也写不进来的管道。
所以实现里必须在 EOF 时清理资源并退出，否则宿主的每次重启都留一堆僵尸进程。
HTTP 传输没有这个问题（连接断就是断），但多了会话管理和鉴权。

**Q：能力协商能不能跳？**
A：跳过能跑通一些玩具场景，但会踩两个坑：一是客户端不知道服务器支持什么，
只能靠「试错」来发现能力（错误处理会变成主要逻辑）；二是版本不兼容时错误出现在很远的地方 ——
典型症状是某个字段莫名其妙缺失。协商的价值就是把「不兼容」提前到连接建立的第一秒。
