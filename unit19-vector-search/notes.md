> 产出不是一个能 search 的函数，而是一组可解释的实验：12 道可答题、6 道无答案题、4 个 K、4 个阈值。

## 本次做了什么

- `store.py`：SQLite 存 float32 BLOB 向量；全量余弦；支持 `top_k`、`min_score`、metadata 白名单过滤。
- `metrics.py`：统一 Recall@K、MRR@K、hits@K；无答案题单独计算检索层误接受率。
- `main.py`：27 段语料（16 正文 + 11 干扰）、12 道可答题、6 道无答案题、FastAPI 与 91 项自检。
- `verify_eval.py`：复现 K 扫描、双侧阈值扫描、干扰对照、过滤、耗时与分数分布。
- `static/index.html`：把可答题误拒和无答案题误接受放到同一张表里。

**2026-11-07 优化修正了三个学习结论**：

1. 旧实现把完整 Top-10 的 RR 用于每个 K，得到恒定 MRR=0.925；现已改成真正的 MRR@K。
2. 旧实现 hits 统计完整列表，导致 Recall@1=11/12 而 hits=12/12；现已统一按 K 截断。
3. 旧讲义把 0.15 产生的空结果当成“本该拒答”；实际上那是一道可答题误拒，同时 4/6 无答案题仍被返回。

## 一、先把指标口径写死

本单元每题只有一条 gold，所以 Recall@K 是单证据 Hit Rate@K：

```text
单题 Recall@K = 1，如果 gold 出现在 Top-K；否则为 0
RR@K          = 1/rank，如果 rank <= K；否则为 0
MRR@K         = 所有可答题 RR@K 的平均值
```

如果一题有多条 gold，Recall 通常是「召回的 gold 数 / gold 总数」，不能直接套这里的二值口径。
无答案题没有 gold，也不应塞进 Recall/MRR；它们要单独评误接受。
标注时还要检查间接答案：「退款能退到他人卡吗」可由「原路退回」作答，不能算无答案；
本组使用「退款手续费由谁承担」等语料确实未规定的问题。

### 一个必须能手算的例子

```text
ranked = [a, b, c]
gold   = b（rank=2）
```

| 指标 | 值 | 原因 |
| --- | ---: | --- |
| Recall@1 | 0 | b 不在前 1 条 |
| Recall@2 | 1 | b 在前 2 条 |
| MRR@1 | 0 | K=1 时按未命中处理 |
| MRR@2 | 1/2 | 首个正确结果排第 2 |

固定同一排序，K 变大时 Recall@K 与 MRR@K 都单调不减，但可能长期持平。
MRR 衡量的是**首个正确结果的排名**，不是精确的噪声条数，也不是答案正确率。

## 二、真实语料的 K 扫描

| K | Recall@K | MRR@K | 命中题数@K |
| ---: | ---: | ---: | ---: |
| 1 | 0.917 | 0.917 | 11/12 |
| 3 | 0.917 | 0.917 | 11/12 |
| 5 | 0.917 | 0.917 | 11/12 |
| 10 | 1.000 | 0.925 | 12/12 |

11 题 gold 排第 1，住宿题排第 10：

```text
MRR@1  = 11/12 = 0.9167
MRR@10 = (11 + 1/10)/12 = 0.9250
```

所以 K 从 3 到 10，Recall、MRR@K、hits@K 一起增加。
旧版表格里 MRR 不随 K 变化，不是“MRR 的特性”，而是实现没有按 K 截断。

## 三、干扰段与语义盲区要分开看

去掉 11 段干扰后的对照：

| 语料 | 住宿题 rank | Recall@1 | MRR@10 |
| --- | ---: | ---: | ---: |
| 16 段正文 | 5 | 0.917 | 0.933 |
| 27 段（含干扰） | 10 | 0.917 | 0.925 |

住宿题：

```text
query: 住宿费一晚最多报多少
gold : 住宿标准：一线城市每晚不超过 600 元，其他城市不超过 450 元。
rank : 第 10 名，gold 分数 cos=0.101
```

本地向量拆字符 bigram：`住宿费/住宿标`、`一晚/每晚` 对不上。
它在干净语料上已经排第 5，因此**语义盲区是第一级原因；近邻干扰只是把它进一步推后**。
不能倒过来写成“去掉干扰就能全对”，那与实测不符。

## 四、阈值实验：空结果不等于拒答成功

### 两组题必须同时看

- **可答题空结果**：误拒（false reject）。库里明明有证据，检索却没返回。
- **无答案题仍有候选**：检索层误接受（false accept）。系统无法再用空结果触发拒答。

检索层误接受不代表 LLM 最终一定误答；生成层仍可能拒答。
但如果检索永远返回 Top-K，单靠“结果为空”的拒答逻辑就一定失效。

`top_k=3` 实测：

| min_score | Recall@3 | 平均返回 | 可答题空 | 无答案误接受 |
| ---: | ---: | ---: | ---: | ---: |
| 无 | 0.917 | 3.00 | 0 | 6/6 |
| 0.1 | 0.917 | 2.67 | 0 | 5/6 |
| 0.15 | 0.917 | 2.08 | 1 | 4/6 |
| 0.2 | 0.833 | 0.92 | 2 | 1/6 |

0.15 的平均返回数少了 31%，Recall@3 没变，但这不足以证明它是好阈值：

1. 住宿题被清空，是可答题误拒，不是“它本来就该拒答”。
2. 仍有 4/6 无答案题返回候选，拒答覆盖并不够。
3. 0.2 把无答案误接受降到 1/6，却同时让 Recall@3 降到 0.833。

**这组扫描点里不存在既保住 Recall@3 又拒绝全部无答案题的阈值。**

### 为什么 Top-1 阈值不够

| 题目组 | Top-1 min | 中位数 | max |
| --- | ---: | ---: | ---: |
| 可答题 | 0.101 | 0.251 | 0.483 |
| 无答案题 | 0.096 | 0.159 | 0.218 |

无答案题最高 0.218，可答题最低 0.101，分布明显重叠。
这与 Unit 18 的 80 题评测结论一致：**不能把单个 Top-1 分数当作可靠的有无答案分类器。**
换 embedder、语料或问题分布后必须重新标定；即使分布分开，也应在独立验证集上选阈值。

## 五、metadata 过滤：条数不变也可能全错

`verify_eval.py` 的过滤对照（top_k=3）：

| 题目集 | 过滤 | Recall@3 | 平均返回 | 空结果题数 |
| --- | --- | ---: | ---: | ---: |
| 全部 12 题 | 无 | 0.917 | 3.00 | 0 |
| 全部 12 题 | `category=refund` | 0.250 | 3.00 | 0 |
| refund 类 3 题 | 无 | 1.000 | 3.00 | 0 |
| refund 类 3 题 | `category=refund` | 1.000 | 3.00 | 0 |

- refund 类题过滤后召回不掉，说明过滤本身正确。
- 非退款题过滤后仍返回 3 条，只是内容不相关；满屏错结果比空结果更容易误导。
- refund 候选有 5 段，大于 top_k=3，所以返回条数不变很正常。
- 过滤评测必须按类目切分题目集，不能把跨类必然失败混成过滤器故障。

实现上必须**先过滤再排序取 K**，且字段名白名单、值参数化。
真实语料是扁平结构，顶层 `category` 要在 upsert 时提升进 meta；测试数据形状必须和真实数据一致。

## 六、工程边界

### 同分排序

`(-score, id)` 是确定性的兜底排序。只按 score 排，同分结果依赖 SQLite 返回顺序，评测无法稳定复现。

### float32 BLOB

512 维固定 2048 字节；JSON 还需要文本序列化与解析。
float32 只有约 7 位有效数字，分数不要直接用 `==` 比较，手算断言要留容差。

### 暴力扫描与 ANN

全量检索复杂度 O(N·d)。本机 2000 条×512 维约 120–140ms/次，瓶颈在 Python 循环和 BLOB 解码。
是否上 HNSW 要看数据量、延迟与 QPS 目标，不是看“别人都用”。
ANN 的候选数也不是 `top_k`；Unit 16 已验证建索引不等于 planner 真用索引。

## 七、完成标准对照

- [x] Top-K 按余弦排序，返回 score、source、page
- [x] Recall@K、MRR@K、hits@K 使用同一 K，有手算例和逐题 rank
- [x] 无答案题不混进 Recall/MRR，单独报告误接受率
- [x] 阈值同时评估可答题误拒与无答案题误接受
- [x] 干扰段与同义改写的影响有对照实验，不归因成单一原因
- [x] 过滤先于 Top-K，白名单和参数化齐全，按类目切分评测
- [x] 所有实测数字可由 `verify_eval.py` 复现

## 一句话总结

检索质量不是“感觉挺准”，而是**可答题看 Recall/MRR@K，无答案题看误接受，调阈值时两侧一起看**；
指标口径、评测集和分数分布没搞清之前，再漂亮的平均值也不能说明系统可靠。

## 面试追问

1. **「MRR 为什么不随 K 变化？」**
   → 如果比较的是 MRR@K，它应随 K 单调不减或持平。恒定不变先检查是否把完整列表 RR 复用于每个 K。
   本单元住宿题排第 10，所以 MRR@1=0.917、MRR@10=0.925。

2. **「Recall@10=1.0，检索是不是没问题？」**
   → 不是。还要在 Top-1/3 命中率、MRR@K、逐题 rank、近邻干扰和真实延迟。
   本单元 11 题排第 1，1 题排第 10；K=3 时那题根本进不了上下文。

3. **「阈值 0.15 能不能用于拒答？」**
   → 不能直接下结论。它让 1 道可答题误拒，仍误接受 4/6 无答案题。
   要同时看两组错误，并在独立验证集上标定；本组数据证明单 Top-1 阈值不够。

4. **「为什么不用 HNSW？」**
   → 2000 条全量扫描约 120–140ms，先对照延迟与 QPS 目标。
   数据量和性能真需要时再上 ANN，并额外评测近似召回相对精确检索的损失。

5. **「过滤放 ANN 前还是后？」**
   → 取决于过滤选择性与引擎能力。高选择性过滤若只在 ANN Top-K 后做，可能一条合格结果都不剩。
   本单元精确扫描采用 SQL 预过滤；pgvector/HNSW 要结合执行计划和候选数实测，不能套固定口诀。
