# Unit 19 笔记 · 向量检索

> 这一章的产出不是一个能search的函数，是一张表：12 题、4 个 K、3 个阈值。
>
> 状态：72 项自检全过（离线，本地哈希向量；SQLite 单文件，不依赖 pgvector）。

## 本次做了什么

- `store.py`：SQLite 存 chunk（float32 BLOB 向量 + JSON meta），`search()` 走全量余弦
  - 支持 `top_k`、`min_score`、`filters`（source / page / category / tenant 白名单）
  - 返回 `SearchResult(hits, scanned, elapsed_ms, ...)`，不只是结果列表
- `metrics.py`：`recall_at_k` / `reciprocal_rank` / `evaluate`，口径只写一次
- `main.py`：27 段语料（16 正文 + 11 干扰）、12 道固定题、`/search` `/eval` `/corpus`
- `static/index.html`：查询 + 阈值滑杆 + 分数条 + K 扫描 / 阈值扫描两张表

## 一、Recall@K 和 MRR 到底在量什么

Recall@K 回答「K 条里有没有对的那条」，MRR 回答「对的那条排第几」。

```
Recall@K = 命中题数 / 总题数
RR       = 1 / rank（未命中记 0）
MRR      = 所有题 RR 的平均
```

这次实测：

| K | Recall@K | MRR |
| ---: | ---: | ---: |
| 1 | 0.917 | 0.925 |
| 3 | 0.917 | 0.925 |
| 5 | 0.917 | 0.925 |
| 10 | 1.000 | 0.925 |

K 从 5 到 10，Recall 从 0.917 涨到 1.000，MRR 一动不动 —— 因为第 10 名那题
贡献的是 `1/10 = 0.1`，它早就算进 MRR 了；Recall 之前漏掉它只是因为截断了。

**只看 Recall 会误判**：12 题里 11 题都在第 1 名，1 题在第 10 名，Recall@10 = 1.0
看起来完美，但实际喂给模型的上下文有 9 条噪声。MRR 0.925 把这个代价记下来了。

## 二、为什么要放干扰段（这章最容易做错的地方）

第一版语料只有 16 段正文，12 题 **Recall@1 = 1.000、MRR = 1.000**。

数字很漂亮，但它证明的是「语料太干净」，不是「检索好用」。任何向量在 16 段
互不相似的文本上都能排对。所以我加了 11 段干扰：和问题共享字词、但不含答案原文。

```
年假结转申请需在次年 1 月 15 日前提交，逾期视为放弃。   ← 干扰段
跨年未休完的年假最多结转 5 天……                        ← 正解
```

加完以后 MRR 掉到 0.925，`年假要提前几天申请` 的第二名变成了 `faq:1:17`。
**评测集的质量决定评测结论**：没有近邻干扰的 gold set，等于没测。

## 三、丢的那一题，正好是这章最该讲的事

```
query: 住宿费一晚最多报多少
gold : 住宿标准：一线城市每晚不超过 600 元，其他城市不超过 450 元。
排名 : 第 10 名（cos = 0.101）
```

字面上看几乎同义，但本地哈希向量拆的是 bigram：
`住宿费` vs `住宿标`、`一晚` vs `每晚` —— 一个都对不上，只剩 `住宿` 两个字撑着。

这不是 bug，是 Unit 15 就写下的结论：**哈希向量验证的是数学，不是语义**。
自检里我把这条写成了断言（`改写过的问法掉出 Top-3`），防止以后有人把
「Recall 掉了」归结成实现问题。

## 四、阈值：拐点要靠扫描找，不能抄

`top_k=3` 时扫 4 档：

| min_score | Recall@3 | 平均返回 | 完全空 |
| --- | ---: | ---: | ---: |
| 无 | 0.917 | 3.00 | 0 |
| 0.1 | 0.917 | 2.67 | 0 |
| **0.15** | **0.917** | **2.08** | 1 |
| 0.2 | 0.833 | 0.92 | 2 |

0.15 是拐点：召回不动，平均返回少 31%，多出来的那条空结果正好是上面那题
（它本来就该拒答）。0.2 开始掉召回 —— 阈值砍过头，连对的也一起剪了。

注意这些分数的绝对值很低（0.1~0.5），因为 512 维里大部分分量是 0。
**换 embedder 后这套阈值全部作废**，必须重扫。抄别人的 0.8 等于没做。

## 五、几个实现上的坑

### 同分排序必须兜底

`hits.sort(key=lambda h: -h.score)` 在分数相同时顺序取决于 SQLite 返回顺序，
不保证稳定。自检里「分数严格降序」那条偶尔红、偶尔绿，就是这个原因。
改成 `(-score, id)` 之后稳定。

### 过滤必须先于排序

先 `LIMIT 5` 再在 Python 里筛 `category`，某个类目可能只剩 1 条，
然后你会去查数据 —— 数据没问题，是顺序错了。

### 字段名和值都要防注入

```python
if key not in FILTERABLE: raise SearchError(...)   # 字段名只能来自白名单
clauses.append(f"json_extract(meta, '$.{key}') = ?")  # 值一律占位符
```

只做值参数化、字段名拼接，一样能注入。这是最常漏的一半。

### 向量存 BLOB 不存 JSON

512 维：struct 固定 2048 字节；JSON 稀疏 2.6 KB、稠密 11.1 KB。
而且 JSON 要 `float→str→float` 转一圈，精度掉在第 7 位，解析还慢一个量级。

### 暴力扫描的真实成本

2000 条 × 512 维，纯 Python 全量扫描 **127 ms/次**。瓶颈是 Python 循环和
BLOB 解码，不是数学。几万条以内暴力完全够用 —— 这就是「要不要上向量库」
第一个该看的数，不是「别人都在用 HNSW」。

## 一句话总结

检索质量不是「感觉挺准」，是 **Recall@K 说能不能找到、MRR 说排得靠不靠前**；
两个数字都由评测集决定 —— 评测集太干净，一切指标都是 1.0，也就什么都没测。

## 面试追问

1. **「Recall@K 都是 1.0，是不是检索就没问题了？」**
   → 先看评测集有没有近邻干扰。16 段互不相似的语料上，任何向量都能排对。
   加 11 段共享词但不含答案的干扰后，MRR 立刻从 1.000 掉到 0.925。
   指标高先怀疑评测集，再怀疑实现。

2. **「阈值该定多少？」**
   → 扫出来的，不是猜的。固定问题集上扫 0.1/0.15/0.2，找「召回不掉、返回最少」那个点，
   本语料是 0.15。分数绝对值还和 embedder 强相关（0~1 都可能），换模型必须重标。

3. **「为什么不用 HNSW？」**
   → 2000 条全量扫描 127 ms，QPS 需求不到 10 的情况下 ANN 没有收益，
   反而引入「结果和精确检索不一致」的新问题。先量 N 和延迟，再谈索引。

4. **「过滤放在 ANN 前还是后？」**
   → 高选择性过滤（只剩几行）放前面，否则 ANN 取回的候选里可能一条都不满足条件，
   结果不足 K 而你以为是没数据；低选择性过滤放后面还能顺便省计算。
   pgvector 的 `ef_search` 要相应调大，这部分在进阶路径里做。
