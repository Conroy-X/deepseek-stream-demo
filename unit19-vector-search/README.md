## 实测（12 题，27 段语料：16 段正文 + 11 段干扰）

| 指标 | 值 | 说明 |
| --- | ---: | --- |
| Recall@1 | 0.917 | 11/12 第一名就中 |
| Recall@3 | 0.917 | 和 @1 一样：中的那 11 题本来就排第一 |
| Recall@5 | 0.917 | — |
| Recall@10 | 1.000 | 丢的那题排到第 10 名 |
| MRR | 0.925 | 一题掉到第 10 → 1/10 拉低均值 |

丢的那题是 `住宿费一晚最多报多少`，gold 段写的是「住宿标准：一线城市每晚不超过 600 元」。
`住宿费/住宿标`、`一晚/每晚` 没有一个 bigram 对得上 —— **本地哈希向量只能匹配字面**，
这就是 Unit 15 说的天花板，换真 Embedding 才会好。这句话不是解释，是自检里的一条断言。

## 阈值扫描（`top_k=3`）

| min_score | Recall@3 | MRR | 平均返回 | 完全为空的题 |
| --- | ---: | ---: | ---: | ---: |
| 无 | 0.917 | 0.917 | 3.00 | 0 |
| 0.1 | 0.917 | 0.917 | 2.67 | 0 |
| 0.15 | 0.917 | 0.917 | 2.08 | 1 |
| 0.2 | 0.833 | 0.833 | 0.92 | 2 |

0.15 是这一版语料的拐点：召回一点没掉，平均返回从 3 条降到 2.08 条（噪声少 31%）。
再往上就开始误伤 —— **阈值不是越高越好，它和模型绑定，换 embedder 必须重标**。

## 四个实现细节（都是坑）

**1. 向量用 struct 不用 JSON**

512 维固定 2048 字节；JSON 是 2.6 KB（稀疏）到 11.1 KB（稠密）。差的不只是体积，
JSON 要走 `float→str→float`，精度掉在第 7 位，而且解析慢一个量级。

**2. 同分必须按 id 兜底排序**

`hits.sort(key=lambda h: -h.score)` 在分数相同时顺序取决于原表顺序，SQLite 不保证稳定。
加上 `, h.id` 之后，自检的「降序」断言才不会偶发失败。

**3. 过滤要写在 SQL 里，且字段名走白名单**

先全局 `LIMIT 5` 再在 Python 里过滤，`category=refund` 可能只剩 1 条，
你会误判成「库里没数据」。字段名拼进 SQL 和值不参数化一样是注入，两个都要防。

**4. 召回口径只能有一份**

Recall 用一套判定、MRR 用另一套，两个数字会互相打架。所以 `_ranked_rows()` 只算一次
有序 id 列表，所有指标都从这一份明细派生。

## 常见坑

- 把余弦相似度当「正确概率」：0.9 只说明方向和 query 接近，不说明答案对。
- `top_k` 当成「候选数」：它是最终返回条数，ANN 的候选数是另一个参数。
- 阈值扫一遍就定死：语料换了、embedder 换了，拐点都会移动，得重扫。
- 只报平均分不看逐题：12 题里 1 题掉到第 10 名，均值看不出来，逐题表一眼就看到。
