## 本次做了什么

`llm_client.py` 一个模块收口五件事：

| 关注点 | 做法 |
| --- | --- |
| 超时 | 统一 `timeout=60`，超时归类为可重试 |
| 重试 | 只重试「再发一次有可能成功」的错误，指数退避 + 抖动 |
| 异常 | 把 SDK 的 8 种异常归一成 6 种自己的类型，每种带 `retryable` 标记 |
| 限流 | 每用户令牌桶，超额返回 429 + `Retry-After` |
| 成本 | 按 `tokens × 单价` 记账，进程内累计到 `/stats` |

上层只剩两行：

```python
content, stats = await client.chat(messages)
async for event in client.chat_stream(messages): ...
```

## 核心一：判断"该不该重试"的唯一标准

不是"什么错误码要重试"，而是：

> **同一个请求再发一次，有没有可能成功？**

| 情况 | 重试？ | 理由 |
| --- | --- | --- |
| 429 限流 | ✅ | 等一下配额就回来了 |
| 500 / 502 / 503 / 504 | ✅ | 上游临时故障 |
| 连接重置 / 超时 | ✅ | 网络瞬断 |
| 400 参数错 | ❌ | 参数不会自己变对 |
| 401 / 403 密钥错 | ❌ | 重试 100 次还是错的，只是浪费配额和日志 |
| 内容审核拒绝 | ❌ | 重试还是被拒 |

这个判断写成数据（`retryable=True/False`）而不是散在 if-else 里，
所以 `normalize_error()` 是唯一需要改的地方。

**教训**：把 400 也纳入重试是很常见的错误 —— 用户传了个超长 prompt，
程序老老实实重试 3 次、每次退避 8 秒，用户等 24 秒拿到一个"参数错误"。

## 核心二：退避必须加抖动

```python
def backoff_delay(attempt, base, cap):
    raw = min(cap, base * (2 ** attempt))   # 0.5, 1, 2, 4, 8...
    return random.uniform(0, raw)           # ← 抖动
```

不加抖动会怎样：100 个客户端同时被限流，它们都按 0.5s、1s、2s 重试，
**时刻完全同步**，于是每次重试都同时撞上去，限流永远解不开。这叫**惊群 / thundering herd**。

`random.uniform(0, raw)` 叫 **full jitter**（AWS 那篇著名的 exponential backoff and jitter）。
它的特点是重试时刻被均匀打散在整个区间，代价是平均等待时间只有 raw/2 —— 比固定间隔更早恢复。

## 核心三：SDK 自带重试的坑

`AsyncOpenAI` 默认 `max_retries=2`。如果我们在外面再包一层 3 次重试，且不关掉它：

```
实际请求数 = 外层 3 × SDK 3 = 最多 9 个请求
```

一次"看起来只重试了 3 次"的调用，账单上是 9 次，日志里还只记了 3 次 —— 排查时会怀疑人生。

所以构造客户端时写死：

```python
AsyncOpenAI(..., max_retries=0)   # 重试只由我们这层负责
```

**通用原则：重试只能有一层。** 要么交给 SDK，要么自己写，不能两套叠加。
如果用 nginx 的 `proxy_next_upstream` 也一样，它也是一种"重试"。

## 核心四：超时不是一个数字

真实项目里至少要区分三种：

| 类型 | 什么时候发生 | 典型设值 |
| --- | --- | --- |
| connect timeout | TCP 都连不上（DNS/网络不通） | 3-5s |
| read timeout | 连上了但迟迟不返回 | LLM 场景要长，30-120s |
| write timeout | 请求体发不出去 | 少见，10s 够 |

LLM 的 read timeout 要**明显长于普通 API**：非流式时模型生成 500 token 可能要 20-30 秒。
如果按普通接口的 5 秒设，你会稳定地拿到一堆超时，然后把重试次数白白烧掉。

流式接口还有个额外好处：**首 token 到达时间（TTFT）本身就是最好的健康指标**。
TTFT 突然从 0.8s 涨到 5s，说明上游在排队，这时候应该降级而不是继续硬扛。

## 核心五：流式重试的额外规则

**第一个 token 到达之后就不能再重试了。**

因为前端已经把这半句话显示出来了，你重发一遍，用户会看到：

```
今天天气很今天天气很不错
```

所以策略是"只在拿到第一个 token 前重试"。这个单元里 `chat_stream` 用 `got_first`
标记来守住这条线，并且在重试时向前端推一个 `retry` 事件，让 UI 能显示"正在重连…"。

这是流式场景和普通请求最本质的区别，面试常问。

## 核心六：令牌桶为什么比固定窗口好

| 方案 | 问题 |
| --- | --- |
| 固定窗口计数 | 边界会被打穿：59 秒打满 N 次，61 秒再打满 N 次，2 秒内过了 2N |
| 滑动窗口 | 好，但要存每次请求的时间戳，内存开销大 |
| **令牌桶** | 按持续速率补充，天然平滑，且允许短时突发（桶里有存货） |

实现只有三行核心逻辑：按流逝时间补令牌 → 够就扣 → 不够就拒。

**多实例部署必须换成 Redis 原子实现**（`INCR` + `EXPIRE` 或 Lua 脚本），
否则每个进程各自算自己的桶，实际放行量 = 实例数 × 配置值。

## 错误码怎么给前端

不要把所有上游错误都变成 500。500 的意思是"我的代码有 bug"，会触发无谓的告警和排查。

| 上游问题 | 给前端 | 含义 |
| --- | --- | --- |
| 没配 key | 503 | 我的配置问题，运维该处理 |
| 上游 401 | 502 | 上游鉴权失败（不是用户的错） |
| 上游 400 | 400 | 用户请求有问题 |
| 重试耗尽 / 上游 5xx | 503 | 暂时不可用，可以稍后重试 |
| 超时 | 504 | 网关超时语义 |
| 本地限流 | 429 + `Retry-After` | 你太快了，等 N 秒 |

## 一句话总结

LLM 应用的稳定性不取决于"模型多强"，而取决于你有没有把**上游当成一个会抖、会限流、
会超时、还会悄悄计费的黑盒**来对待：只重试该重试的，退避要带抖动，
超时要按场景给足，流式一旦出字就不再回头。

## 面试追问

1. **「重试会不会导致重复计费 / 重复执行？」**
   → 重试本身不是幂等的。查询类调用重试没问题；写操作（下单、扣款）必须带幂等键，
   或者干脆不自动重试。LLM 生成属于"只读但计费"，重试会重复消耗 token，所以要限制次数并记账。

2. **「怎么防止用户把 API 额度刷爆？」**
   → 三层：入口限流（令牌桶，按用户）→ 单次请求上限（max_tokens）→ 日/月累计配额。
   只做第一层，用户换个账号就绕过；只做第三层，攻击者一夜之间就能烧光月配额。

3. **「重试次数怎么定？」**
   → 看上游 SLA 和用户耐心。3 次是个常见平衡点（0.5+1+2 = 3.5 秒额外等待）。
   用户能等的交互式场景 2-3 次；离线批处理可以 5 次以上。

4. **「超时设多少？」**
   → 非流式要看最长响应时间，LLM 生成 500 token 可能要 20-30 秒，给 60 秒不夸张。
   流式接口应该看 TTFT 而不是总时长，卡住的是首字，不是全文。

5. **「多个实例限流怎么算？」**
   → 单机内存限流只在单实例成立。多实例必须用 Redis 做共享计数器，
   否则 4 个实例各配 20 次/分，实际就是 80 次/分。

## 补充详解（2026-10-25 补课）

> 这四个问题是「看懂单个单元」和「能上生产」之间的坎。答案都对着本单元的代码讲。

### A. HTTP 状态码：4xx 是「你错了」，5xx 是「我错了」

一句判据：**4xx = 客户端原样重发没用（要改请求）；5xx = 服务端这边的问题（稍后可能好）。**

| 码 | 名字 | 真实含义 | 本单元/前几个单元的例子 |
| --- | --- | --- | --- |
| 400 | Bad Request | 请求本身不合法（JSON 语法错、类型不对） | 上游说参数不合法 |
| 401 | Unauthorized | **没认证**或凭证无效（名字有坑，它其实是"未认证"） | 没配 key / token 过期 |
| 403 | Forbidden | 认证过了，但没权限 | 别人的会话 |
| 404 | Not Found | 资源不存在；也常用来**掩盖越权**（不说"存在但你不能看"） | unit12/14 越权一律 404 |
| 405 | Method Not Allowed | 方法不对 | GET 打了 `POST /conversations` |
| 409 | Conflict | 与现有状态冲突 | 重复邮箱 |
| 422 | Unprocessable Entity | 语法对但**语义校验**不过 | Pydantic `Field required`；登录用 JSON 打表单接口 |
| 429 | Too Many Requests | 你太快了（限流），**应带 `Retry-After`** | 令牌桶拒绝 |
| 499 | （Nginx 自定义） | 客户端主动断开，服务端还没回 | 点「停止」、关页面 |
| 500 | Internal Server Error | **我的代码有 bug**（会触发告警、要人排查） | 就是你踩过的「st 未定义」 |
| 502 | Bad Gateway | 网关拿到的上游响应无效（上游挂了/返回了非 HTTP） | 上游 401 转 502 |
| 503 | Service Unavailable | 服务暂时不可用（过载、维护、依赖没就绪） | 没配 key、重试耗尽 |
| 504 | Gateway Timeout | 网关等上游超时 | LLM 超时 |

几个高频混淆点：

- **401 vs 403**：401 是"你是谁我不知道"，403 是"我知道你是谁，但你不能干这个"。
- **400 vs 422**：400 更偏"报文层面就不对"，422 是"报文能解析，但字段校验不过"。FastAPI 校验失败统一给 422。
- **429 vs 503**：429 是"你的节奏问题"（你等一会儿还能来），503 是"我这不行"（跟你的节奏无关）。
- **499/断线**：客户端走了，服务端要做的不是返回错误码，而是**把已生成的内容存下来**（unit14 那个 bug）。

#### 为什么上下游错误码不能直接透传

关键认知：**前端只跟"你"签合同，不跟 DeepSeek 签。** 上游的码是"上游对我说的话"，不是"我要对前端说的话"。

四个理由：

1. **语义错位会误导前端逻辑**。上游 401 的含义是"你给我的 key 无效"。如果原样透传 401，前端会按"用户登录态失效"处理——把用户踢回登录页。可用户明明刚登录过，真正的故障是你的 key 配错了。
2. **可操作性错位**。前端看到 400 会提示"请修改输入"；如果这个 400 其实是你拼 prompt 拼错了（你的 bug），前端引导用户改输入就是纯误导。
3. **安全**。上游错误体里可能带 endpoint、key 前缀、账号信息。透传等于把内部细节交给浏览器。
4. **可观测性**。5xx 率应该精确代表"我们的问题"。把上游 429 透传成 429，你的 4xx 曲线会被上游情绪污染，真正的用户错误反而看不出来。

#### 本单元的映射（`main.py` 的 except 分支）

| 上游/内部问题 | 给前端 | 理由 |
| --- | --- | --- |
| 没配 key（`LLMConfigError`） | **503** | 运维可修的配置问题，不是代码 bug，更不是用户的错 |
| 上游 401（`LLMAuthError`） | **502** | "上游拒绝了我"，属于网关视角的坏响应 |
| 上游 400（`LLMBadRequestError`） | **400** | 确实是请求有问题（注意：如果是自己 prompt 的锅，这里该改成 500 并告警） |
| 重试耗尽（5xx/限流） | **503** | 暂时不可用，前端可稍后重试 |
| 超时（`LLMTimeoutError`） | **504** | 网关超时语义，和"服务挂了"区分开 |
| 本地限流 | **429 + `Retry-After`** | 让客户端知道"等几秒"，而不是盲猜 |

规律：**5xx 里再细分——502 是"上游给了坏响应"，503 是"我这不可用"，504 是"等超时了"。**
只有真正的代码 bug 才该出现 500。

#### 错误体建议：别只给一个状态码

```json
{
  "error": {
    "code": "rate_limited",
    "message": "请求过于频繁，请 3 秒后再试",
    "retry_after": 3,
    "request_id": "req_8f2c...",
    "upstream_trace": "x-ds-trace-id 的值"
  }
}
```

- `code`：给程序判断（**不要用 message 判断**，文案随时会改）
- `message`：给人看
- `retry_after` / `Retry-After` 头：给重试策略
- `request_id`（+ 上游 trace id）：给排查。Unit 3 学过的 `x-ds-trace-id` 就是干这个的

### B. 限流方案里的四个名词

先把词讲清，再讲为什么令牌桶好。

| 名词 | 一句话 | 状态开销 |
| --- | --- | --- |
| **固定窗口计数器** | 时间切成等长窗口（每分钟一格），每格一个计数，超了就拒，窗口一到清零 | O(1) |
| **滑动窗口日志** | 记下每次请求的时间戳，判断"最近 60 秒内几次" | O(N)，N=窗口内请求数 |
| **滑动窗口计数** | 固定窗口 + 用上一格的计数按比例折算，近似出滑动效果 | O(1) |
| **令牌桶** | 桶容量 C，按速率 r 持续补令牌；请求消耗令牌，不够就拒 | O(1) |
| **漏桶** | 请求排队，按固定速率流出；输出绝对平滑、**不允许突发** | O(队列长度) |
| **并发限流** | 限制"同时正在处理"的请求数 | O(1) |

**固定窗口的边界突刺**（这就是笔记里那句话的意思）：

```
配额 100 次/分钟
12:00:59  打了 100 次 → 本窗口配额用光，全部放行
12:01:00  窗口重置，计数归零 → 再打 100 次，又全部放行
结果：2 秒内通过 200 次 = 配额的 2 倍
```

**令牌桶为什么没这个问题**：它不"重置"，而是按时间**连续**补令牌。上面那 2 秒里，
桶最多也就补回 `r × 2` 个令牌，多出来的请求一律拿不到令牌。

**令牌桶两个参数的物理含义**（这是它最强的地方）：

- `capacity`（桶容量）= **允许多大的突发**。桶里存着 C 个令牌，意味着"空闲一会儿之后，用户可以一次性连打 C 次"。
- `refill_per_sec`（补充速率）= **长期平均速率**。

两个旋钮分开调：想允许交互式突发但限制长期量 → 容量给大、速率给小。
固定窗口只有一个旋钮（每窗口 N 次），表达不了"突发"和"平均"的区别。

**本单元的参数换算**（`PerUserRateLimiter`）：`per_minute=20` →

```python
TokenBucket(capacity=20, refill_per_sec=20/60)   # 每 3 秒补 1 个令牌
```

实测（容量 20 的桶连打 21 次）：

```
前 20 次：全部通过（桶里的存货一次用光）
第 21 次：拒绝，retry_after = 3.0 秒   ← 缺 1 个令牌 ÷ 每秒 1/3 个 = 3 秒
等 3.2 秒再试：通过
```

`retry_after()` 的算法就是"还差几个令牌 ÷ 补充速率"，所以 429 能给出**准确的** `Retry-After`，
而不是拍一个固定值。

**令牌桶的三个坑**：

1. **单机内存 ≠ 全局限流**。4 个实例各配 20 次/分，实际放行 80 次/分。多实例必须 Redis 原子实现
   （`INCR + EXPIRE`，或 Lua 脚本保证"补令牌+扣令牌"原子）。
2. **桶要能过期回收**。本单元用 `dict[key] = bucket`，长期运行会累积大量空桶（内存泄漏）。
   生产上加 LRU 或 TTL。
3. **令牌桶管不住"单次请求多贵"**。它只数"次数"，一次 4096 token 和一次 16 token 都是 1 个令牌。
   所以必须配合 `max_tokens` —— 正好是下面第 D 题。

### C. TTFT 是什么

**TTFT = Time To First Token，从发出请求到收到第一个内容 token 的耗时。**

为什么它比"总耗时"更值得盯：

- 用户感知的是**"多久开始有反应"**。0.8 秒出第一个字 vs 8 秒才出第一个字，体验差一个量级。
- 流式下**总耗时不可比**：回答 100 字和 1000 字的总时长天然不同，但 TTFT 只反映"前期健康度"。
- 它是**唯一能提前发现上游排队**的指标。等总耗时变长时，用户早就骂完了。

一次请求的时间构成：

```
[网络 RTT] → [上游排队] → [预填充 prefill：读 prompt、建 KV cache] → [第 1 个 token] → [后续 token...]
             └─────────────── TTFT 覆盖这一段 ───────────────────┘        └── TPOT 覆盖这段 ──┘
```

三个配套指标：

| 指标 | 含义 | 公式关系 |
| --- | --- | --- |
| **TTFT** | 首字延迟 | — |
| **TPOT / ITL** | 每个输出 token 的间隔（出字速度） | 总耗时 ≈ TTFT + TPOT × 输出 token 数 |
| **吞吐** | tokens/秒 | ≈ 1 / TPOT |

本单元的实测值：`first_token` 事件的 `ttft` 在 0.76–1.16 秒（`deepseek-flash`，短 prompt）。

**一个必须知道的坑**：`deepseek-flash` 是推理模型，它先"思考"再出正文。
本单元的 `ttft` 是在**第一个 `content` delta** 时打点，所以**包含了整段思考时间**——
同一个问题，简单问法 0.8 秒，需要推理的问法可能要 5–10 秒，这完全正常，不是慢。

怎么用它：

- 监控 **P95 TTFT**，而不是平均值（平均值会被大量快请求掩盖）。
- TTFT 从 0.8s 涨到 5s → 上游在排队，该降级/切备用/提示用户，而不是硬扛。
- 熔断规则可以是"连续 N 次 TTFT > 阈值 → 暂停 30 秒"，比等超时快得多。

### D. 怎么防止用户把 API 额度刷爆

先算最坏情况，才知道为什么"加了限流"远远不够（按本单元 `.env` 的单价
`输入 1 元/M、输出 2 元/M`、`per_minute=20`、`max_tokens=4096`）：

```
单用户峰值：20 次/分 × 4096 输出 token ≈ 8.2 万 token/分
          ≈ 4.9M token/小时
          × 2 元/百万 ≈ 9.8 元/小时
一天（24h 不停）≈ 236 元 / 用户
```

注册 100 个账号刷一天 → 两万多块。**限流只限制了"频率"，没有限制"总量"。**

所以要四层，缺一层都能被绕：

| 层 | 管什么 | 具体做法 | 本单元现状 |
| --- | --- | --- | --- |
| **L1 频率** | 单位时间几次 | 按 `user_id` 令牌桶 + 429 + `Retry-After`；注册/登录接口也要限流（防批量注册） | ✅ 已有 |
| **L2 单次** | 一次请求最多花多少 | `max_tokens` 上限、prompt 长度上限、历史条数上限；超长直接 400/422 | ✅ `max_tokens` 有；prompt 长度只在 unit14 的 `MAX_CONTEXT_MESSAGES` 管了"条数" |
| **L3 配额** | 一天/一月总共多少 | 日/月 token 预算落库，超限拒绝或降级 | ❌ 缺（`/stats` 只记全局，没有按用户） |
| **L4 熔断** | 异常模式 | 全站日预算；单用户 1 分钟成本突增告警；同一 prompt 高频重复自动封禁 | ❌ 缺 |

再加两条"防绕过"：

- **限流维度必须是登录用户，不能只按 IP**。按 IP 会被代理池绕过；反过来 NAT 后面的正常用户会被误伤。
- **免费额度与付费额度分池**。免费池的日配额要小得多（比如 5 万 token/天），付费池按购买量。

L3 的最小可用实现（面试可以直接讲这段）：

```sql
-- 一张配额表
create table usage_quota (
  user_id   bigint not null,
  day       date   not null,
  tokens    bigint not null default 0,
  cost_cny  numeric(12,6) not null default 0,
  primary key (user_id, day)
);

-- 关键：用一条语句"原子地抢占额度"，避免并发超卖
update usage_quota
   set tokens = tokens + :need
 where user_id = :uid and day = current_date
   and tokens + :need <= :limit
returning tokens;
-- 没有返回行 = 额度不够 → 429/402，提示"今日额度已用完"
```

放在哪里：**调用模型之前**先按本次 `max_tokens` 预占额度，调用结束后用真实 usage 多退少补。
这样即使调用失败也不会超卖，也不会因为并发把额度打穿。

L4 的检查清单（上线前过一遍）：

- [ ] 全站日预算告警（比如日花费 > 50 元就发通知）
- [ ] 单用户 1 分钟成本突增告警（比如 > 1 元）
- [ ] 同一账号 10 分钟内相同 prompt 超过 N 次 → 疑似脚本，先限速再谈封禁
- [ ] 关键指标进监控：429 率、5xx 率、P95 TTFT、单次平均成本、日总成本
- [ ] 有"一键降级"开关：把模型切到更便宜的、把 `max_tokens` 砍半、或直接关闭非核心功能

**一句话总结这题**：限流管频率、`max_tokens` 管单次、配额管总量、熔断管异常、身份管绕过——
五件事分开做，任何一层单独上都不够。
