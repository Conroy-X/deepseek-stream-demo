## 为什么要"两段式"

| | 向量召回（双塔） | 重排（交叉） |
| --- | --- | --- |
| 计算 | query / doc 各自编码，可预计算 | query 与 doc 一起打分 |
| 复杂度 | O(1) 查索引 | O(N) 逐条算 |
| 准确度 | 粗，只看"整体像不像" | 细，能看"到底回答了没有" |

所以工业界的固定套路是：**召回 20–50 条 → 重排取 3–5 条**。
对全库重排不是"更准"，是算不起。

## 实测（本单元最重要的数据）

23 条语料（含 2 条关键词堆砌页），6 道题，`top_k=5`：

| 分组 | MRR（向量） | MRR（+重排） |
| --- | ---: | ---: |
| 短问题（3 题） | 0.833 | 0.833 |
| 长问题（3 题） | 0.833 | **1.000** |
| 合计 | 0.833 | **0.917** |

关键那一题：

```
账号密码输错几次会被锁，锁了找谁解锁？
  向量首条 = rl-3（P1 事故 24 小时内出初稿）   ← 被"锁"这种字面噪声带偏
  重排首条 = sc-2（连续 5 次登录失败锁定账号 30 分钟）  ✅
```

**短问题没提升是正常现象**：一句话一个意图，向量的整体相似度已经够准，
重排只是确认一遍。重排的价值集中在"一句话混了好几个意图"的长问题上。

## 重排救不了什么（诚实的部分）

语料里放了一条 SEO 式堆砌页：

```
退款 退款多久到账 退款流程 退款说明 退款查询 退款进度 退款到账 退款政策 …
```

问「退款多久到账」时，**向量和 BM25 都把它排在第 1**。

BM25 有 IDF、有长度归一化，理论上该压住堆砌 —— 但这条页面把 query 的
每个 bigram 都塞满了，tf 饱和之后照样给高分。**字面手段的天花板就在这里。**

要治它只有语义重排（bge-reranker / Cohere Rerank），那需要装模型，
本仓库为了"clone 下来就能跑"没有引入。

## 实现上的三个决定

**1. IDF 在候选集内算，不在全库算**

```python
idf[t] = log(1 + (N - df[t] + 0.5) / (df[t] + 0.5))
```
候选集只有 20 条时，这个 IDF 只在本批内可比 —— 够用来排序，但不能跨查询比分数。
真 CrossEncoder 直接输出相似度，没有这个问题。

**2. 保留 `vector_rank`**

重排完还留着原始向量排名，UI 上才能显示"↑2 / ↓1"。
线上排查"为什么这题被挤下去了"，靠的就是这两个数。

**3. 先排序再截断，且截断在重排之后**

召回阶段取 20（`recall_n`），重排后才取 5（`top_k`）。
如果召回就只取 5，重排没有任何腾挪空间 —— 那等于没做重排。
