# Unit 24 笔记 · Embedding 流水线

> 状态：67 项自检全过，**连跑两次都是 0 失败**（离线，本地哈希 provider，不需要 key）。这一单元的重点不是"生成向量"，
> 而是**让这段外部调用可重跑、可计费、可解释**。

## 本次做了什么

- `pipeline.py`：provider 抽象 + 组批（条数/token 双约束）+ 指数退避 + 一批一事务 + 台账；`chunks` 表带 `status/attempts/vector/model/dim/est_tokens/act_tokens`，`runs` 表记每次运行
- `main.py` 7 个接口 + 67 项自检；`static/index.html` 控制台 + 状态看板 + 批次明细 + batch 对比表；库在 `data/emb.db`

## 一、批量的收益：调用次数，还有事务数

100 条演示 chunk、512 维，两种批量各跑一遍：

| batch_size | 调用次数 | 事务数 | 本地耗时 | token | 成本 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 100 | 100 | 29 ms | 2270 | $0.000295 |
| 16 | **7** | **7** | 11 ms | 2270 | $0.000295 |

两行 token 一模一样 —— 批量**不省 token，只省次数**。限流按次数算，重试代价也按次数翻倍。
29 vs 11 ms 只差 2.6 倍，看着没说服力；把 `synchronous` 从 NORMAL 换回默认的 FULL，同一条流水线：

```text
FULL   100 次单独 commit 11530 ms（每次 115 ms）· 一次批量 354 ms
NORMAL 100 次单独 commit 0.7 ms（每次 0.01 ms）· 一次批量 0.1 ms
```

batch=1 从 29 ms 变成 11.5 秒 —— 时间全在 fsync。**批请求也是批事务**：一个事务写 16 条，fsync 只做一次。
生产用 WAL + NORMAL 是 SQLite 官方推荐（进程崩溃不损坏库，最坏丢最后一次事务）；
但换 Postgres 也一样要算这笔账：每个事务仍是一次 WAL flush。

## 二、429 不是异常，是常态

注入前 2 次必失败、`max_retries=2`：第 1 批 **3 次尝试**后成功（退避 0.01 → 0.02 s），第 2 批 1 次。三个细节：

1. **总尝试 = 1 + max_retries**。`max_retries=2` 是"首次 + 2 次重试"，不是"试 2 次"。
2. **失败的调用不计 token**：没有 usage 就没有账单，32 条只花 32 条的 token。
3. **重试要分类型**：429/超时进循环；401、返回条数对不上立刻抛 —— 重试 401 一百次还是 401，只是账单乘以一百。

退避用 `delay * 2^(n-1)` 封顶 0.5 s。本单元**故意没加抖动**（自检要断言 `[0.01, 0.02]` 的确切值），
生产必须加 ±25%：故障恢复时所有 worker 同时重试，会把刚缓过来的服务再打一次。

## 三、续跑的锚点是"每条的完成事实"

```python
# ✗ 按位置：offset 一旦和实际写入错位，就漏条或重算
rows = SELECT * FROM chunks WHERE seq > last_offset
# ✓ 按状态：锚点是每条自己的事实
rows = SELECT * FROM chunks WHERE status != 'done'
```

实测（100 条，batch=16）：

| 轮次 | 投喂 | 调用 | 本轮完成 |
| --- | ---: | ---: | ---: |
| 跑到 40 条中断 | 40 | 3（16+16+8） | 40 |
| 续跑 | **60** | **4**（ceil(60/16)） | 60 |
| 再跑一次 | 0 | **0** | 0 |

3 + 4 = 7，正好等于全量一次跑完的调用数 —— 续跑**没有重算任何一条**，第三轮 0 次调用 0 元。`failed` 也算"未完成"，会被下一轮捡回来；否则那批永远停在 failed，只能改库或全量重跑。

## 四、向量和状态必须同一个事务

注入 `c003` 写入失败（模拟 `database is locked`）：

| 观测点 | 结果 |
| --- | --- |
| `c003` 状态 | `failed`（不是 `done`） |
| 同批 `c000` 状态 | `failed`（**也被回滚**） |
| 库里向量数 | 16（只有另一批，无半写） |
| 修好后重跑 | 1 次调用补齐 16 条 |

分开提交会留下两种残缺："向量有、状态 pending" → 下次重算，钱白花；"done 但没向量" → 检索永远查不到，还不报错。**第二种更可怕，因为它是静默的。**

## 五、token 与成本：估算只管组批

100 条：估算 2201、实际 2270，偏差 **3.0%**，按 $0.13/1M 计 **$0.000295**。

3.0% 有水分 —— 本单元估算和计数用了同一套字符系数。真实 BPE 下经验公式偏 10–20% 是常态，所以：
估算只用于**组批和预算**（发请求前要知道一批塞多少），实际只用于**账单**（`usage.total_tokens`）。两个都记，才知道预算偏了多少。

## 完成标准对照

| 要求 | 证据 |
| --- | --- |
| 批量调用，不是一条一发 | 100 条：100 次 → 7 次，token 不变 |
| 限流重试能挺过去 | 注入 2 次 429，3 次尝试成功，`attempts=3` 落库 |
| 断点续跑只处理剩余 | 中断 40 → 续跑只投喂 60 条、4 次调用 |
| 已完成的不重复计费 | 累计 token = 一次全量的 2270，不是 2 倍 |
| 版本与维度可追溯 | `model=local-hashing-512`、`dim=512` 逐条落库 |
| 估算 vs 实际有量化 | 2201 vs 2270，偏差 3.0% |
| 写库失败不标 done | 整批回滚，16 条全 failed，无半写向量 |

## 一句话总结

embedding 流水线的正确性不在向量里，在**状态表**里：只要每条 chunk 的 status 可信，重跑就永远安全；成本可控的前提是"调用次数"和"token 数"分开记账。

## 面试追问

1. **「批量多大合适？」**
   → 三个上限夹：单请求条数（常见 16–2048）、请求体 token 上限、一批失败重试的浪费。从 16 起，按 p99 延迟和 429 率调，再用 token 预算兜底，别让一条超长文本把整批撑爆。

2. **「断点续跑为什么不记 last_offset？」**
   → offset 是**位置**，"写成功的条数"是**事实**，并发/重试/部分失败都会让两者错位。可靠做法是幂等 + 事实驱动：唯一键 `(chunk_id, model, dim)`，重跑只处理没 done 的。

3. **「429 重试怎么设计才不把服务打死？」**
   → 指数退避 + 上限 + 抖动，尊重 `Retry-After`，只重试可重试错误，并给每次运行设总预算（最大调用数 / token），超了主动停。没有上限的重试在故障时就是一次自伤。

4. **「成本怎么估才靠谱？」**
   → 两个数都要：事前估算（组批/预算，允许 10–20% 误差）、事后实际（provider usage，用于账单）。每次运行落一条台账，"重跑一次多少钱"才是可查的数字 —— 估算长期偏低就修系数，别修账单。
