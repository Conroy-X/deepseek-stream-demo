# Unit 24 · Embedding 流水线

> 把 chunk 稳定地变成向量：批量调用、限流重试、断点续跑，并且知道这次到底花了多少 token 和钱。

**完成标准**：能拿出「100 条 batch=1 要 100 次调用、batch=16 只要 7 次」的数字，能说清中断后重跑为什么不是全量重来，能报出这一轮的成本到小数点后六位。

## 快速开始

```bash
cd ~/ai-journey/unit24-embedding-pipeline
uv sync
uv run uvicorn main:app --reload --port 8024
```

打开 <http://127.0.0.1:8024/>：先「灌数据」100 条，再「跑一批」；把「只跑前 N 条」填成 40、注入 429 填 2、max_retries 填 2，点「跑一批」看第 1 批怎么用 3 次尝试挺过去。

## 自检

```bash
uv run python main.py
```

67 项，全离线、不需要 key（连跑两次都是 0 失败）：

- **批量**：100 条 batch=1 → 100 次、batch=16 → 7 次；token 与批量无关；token 预算另切一刀
- **重试**：前 2 次 429 → 第 3 次成功，`attempts=3` 落库，退避 `[0.01, 0.02]`；用尽则该批 `failed` 而非静默丢弃
- **续跑**：跑 40 条中断 → 续跑只投喂 60 条、4 次调用 → 第三次 0 次调用 0 元
- **向量**：维度 512、范数 ≈ 1、自比余弦 = 1、同文本两次结果完全一致
- **成本**：估算 2201 vs 实际 2270（偏差 3.0%），重跑不重复计费
- **写库失败**：注入 `c003` 写入失败 → 整批回滚，16 条全 `failed`、一条 `done` 都没有

## 实测

100 条演示 chunk，本地哈希 provider，512 维：

| batch_size | 调用次数 | 事务数 | 本地耗时 | token | 成本 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | **100** | 100 | 29 ms | 2270 | $0.000295 |
| 16 | **7** | 7 | 11 ms | 2270 | $0.000295 |

两行 token、成本完全一样，省下来的是**请求数**和**事务数**（线上还要再乘一次 100–300 ms 的 RTT）。
耗时只差 2.6 倍，看着没说服力 —— 那是因为我用了 WAL + `synchronous=NORMAL`。换回默认 `FULL` 再测：

```
FULL   100 次单独 commit 11530 ms（每次 115 ms）· 一次批量 354 ms
NORMAL 100 次单独 commit 0.7 ms（每次 0.01 ms）· 一次批量 0.1 ms

注入 2 次 429，max_retries=2 → 第 1 批 3 次尝试（退避 0.2 → 0.4 s），第 2 批 1 次
跑 40 条中断 → 3 次调用（16+16+8）；续跑 60 条 → 4 次调用；第三次 → 0 次调用
估算 2201 / 实际 2270 token（偏差 3.0%，按 $0.13/1M 计 $0.000295）
```

同一条流水线，只是 PRAGMA 不同，batch=1 就从 29 ms 变成 11.5 秒。**批请求也是批事务。**

100 条小片段只要三厘钱，所以**成本不是这个单元的瓶颈**。真实语料 10 万 chunk × 400 token = 4000 万 token ≈ $5.2/次全量重建 —— 这才是"重跑不能重算"值钱的地方。

## 常见坑

**1. 续跑的锚点是「每条的完成事实」，不是 offset。** `WHERE status != 'done'`，不是 `WHERE seq > 上次跑到哪`。offset 一旦和实际写入错位就会漏条或重算，而重算就是重付钱。`failed` 也算未完成，所以会被续跑捡回来。

**2. 向量和 status 必须同一个事务。** 先写向量再改状态，中间崩一次就留下"向量有了但状态还是 pending"的孤儿，下次重算一遍；反过来"done 但没有向量"更糟：检索永远查不到，还不报错。

**3. 重试要分可重试和不可重试。** 429 / 超时 → 退避重试；400 / 401 / 返回条数对不上 → 立刻失败。重试一个 401 一百次也是 401，只是把账单乘以一百。

**4. 估算 token 天生不准。** 本单元 3.0% 的偏差是因为估算和计数用了同一套系数；真实 BPE 下经验公式偏 10–20%。估算只能用来组批和做预算，账单必须用 provider 返回的 `usage.total_tokens`。

**5. 退避必须加抖动，但本单元故意没加。** 自检要断言 `[0.01, 0.02]` 这个确切值，所以没抖。生产必须加 ±25% 随机抖动：故障恢复时所有 worker 同时重试，会把刚缓过来的服务再打一次。
