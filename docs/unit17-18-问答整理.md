## 1.2 decode_bytes 解析

```python
def decode_bytes(data: bytes) -> tuple[str, str]:
    for enc in ("utf-8-sig", "utf-8", "gb18030", "big5"):
        try:
            return data.decode(enc), enc
        except UnicodeDecodeError:
            continue
    return data.decode("utf-8", errors="replace"), "utf-8(replace)"
```

**解决的问题**：上游拿到的是裸字节，字节本身没有"我是 UTF-8 还是 GBK"的标签。同一段字节用错编码解，出来的是乱码——而且乱码**不报错**，会一路流进 chunk、向量、检索结果。任务：猜对编码，猜不出就大声标记。

**尝试链顺序是核心设计**（越靠前越严格）：

- `utf-8-sig` 最前：带 BOM 的 UTF-8。BOM 是文件头 3 个隐形字节 `\xef\xbb\xbf`，用普通 utf-8 解会变成正文第一个字符（`\ufeff`），肉眼不可见但会跟着第一块文本一起变成向量——之后检索永远匹配不上第一块。`utf-8-sig` 的作用就是剥掉 BOM
- `gb18030` 必须排在 utf-8 后：它的编码空间几乎覆盖全部字节组合，**几乎能"成功"解码任何输入**。排在前面的话，正常 UTF-8 中文文件会被它"成功"解成汉字乱码且不抛异常——顺序错了，编码侦探变乱码制造机
- `big5` 放最后：繁体文件如果连 gb18030 都解不动才轮到它

**兜底路径不抛异常但留标记**：`errors="replace"` 把解不了的字节换成 `�`（U+FFFD），并返回特殊编码名 `"utf-8(replace)"`——调用方看到这个名字就往 `warnings` 塞一条。原则：**warnings 不是装饰**——扫描件、DOCX 无分页、编码兜底，三种"文件不完美"都必须显式浮出水面。

## 1.3 /parse 路由的 multipart 处理在哪

```python
@app.post("/parse")
async def parse_upload(file: UploadFile = File(...)) -> dict:
    data = await file.read()
```

`file: UploadFile = File(...)` 这一个参数注解**就是** multipart 处理的全部入口——不是没处理，是 Starlette（FastAPI 底层）折叠了它。

浏览器上传时 HTTP 请求是 `multipart/form-data`（按 boundary 切分、每个 part 带 `Content-Disposition` 头、filename、内容类型）。如果手写，得自己切分字节流、解析每个 part 的头。Starlette 看到 `UploadFile` 注解自动做完这一切，把文件打包成对象递给你。`UploadFile` 大文件会落盘暂存，不会撑爆内存。

**对照组**：`/parse-text` 用 JSON body 传文本，绕开 multipart 方便测试和自检。两个路由最终汇入同一个 `parse_bytes`——HTTP 层薄，解析逻辑集中。

面试标准答案：**声明 `UploadFile = File(...)`，框架负责 multipart 协议解析和流式暂存，业务代码只消费字节**。可对比 Flask 的 `request.files`（同步、全量进内存）。

## 1.4 utf-8 解析失败报什么错

报 `UnicodeDecodeError`（`ValueError` 子类）——正是 `except UnicodeDecodeError: continue` 捕获的。实测：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd6 in position 0: invalid continuation byte
```

异常对象带定位信息：`e.start/e.end`（坏在第几个字节）、`e.reason`（原因）。

**为什么 UTF-8 能"验出来"是错的**——它是自校验编码，字节结构有硬性规则：

```
首字节：    0xxxxxxx（ASCII）/ 110xxxxx（2字节开头）/ 1110xxxx / 11110xxx
后续字节：  必须是 10xxxxxx（continuation byte）
```

GBK 的"中"是 `D6 D0`：`D6` 以 `110` 开头被当成 2 字节序列开头，下一字节 `D0` 最高两位是 `11` 而非规定的 `10`——规则被违反，当场抛错。**合法 UTF-8 字节流极少能同时满足另一套编码的规则**，所以"utf-8 先试、炸了换下一个"才可靠。

一句话：utf-8 的报错是探测机制的"否决票"，链上每个编码依次投票，第一个不否决的当选——而 gb18030 是老好人几乎从不否决，所以只能排后面。

## 1.5 为什么 big5 放最后

不是技术必然，是**优先级赌注**。实验证明 gb18030 和 big5 **互相解码都不报错、只出乱码**（"學習中文"被 gb18030 解成"厩策いゅ"）——两套编码字节空间重叠太大，任何一方的文件喂给另一方都能"成功"解出错字。

所以 for 循环的裁决规则是"谁先成功谁赢"，而 gb18030 与 big5 之间没有任何技术手段分出对错——**放在哪个位置，纯粹是赌"进来 more 的文件是简体还是繁体"**。面向大陆用户的知识库，gb18030 排前；如果面向台湾用户，顺序就该倒过来。

**已知的无警告失败模式**：繁体 Big5 文件大概率被 gb18030 抢先解走 → 错字乱码 → warnings 里什么都没有。比 `�` 兜底还隐蔽，因为错字是合法汉字。面试标准答法：逐个 try 只适合"一个明确主编码 + 少量例外"的场景；精确区分简繁要上统计式探测（chardet/uchardet，按字符频率分布打分）。

## 1.6 为什么只归一全角字母数字，不用 NFKC

NFKC（Unicode 兼容性归一化）会把全角折叠成标准形式：`ＡＢＣ→ABC`、`（，：）→(, :)`、`ﬁ→fi`、`①→1`。为什么这里故意只用 62 字符的手工翻译表（`_FULLWIDTH_ALNUM`）？

**理由一：全角标点是中文排版的一部分，不是脏数据**

```
原文：    公司（成立于２０２０年），主营：AI。
NFKC 后：公司(成立于2020年), 主营: AI.   ← 英文标点，中文文档瞬间"变味"
```

`，` 和 `,` 不是同一个东西的两种写法，前者是中文标点体系的一员。

**理由二（更致命）：Citation 要展示原文片段**

RAG 管线的引用要把原文片段展示给用户并标注页码。归一化改了标点，检索命中后高亮的片段和用户手里那份原始文档**对不上**——"引用可核对"这个 RAG 核心信任机制就断了。改动越少，越对得上。

**那为什么全角字母数字可以归**：`２０２０` 和 `2020` 几乎总是"同一个意思的意外产物"（输入法没切半角）。归一它们：视觉几乎无差别、检索收益大（数字/型号/年份是高频检索词）、不破坏标点体系。

**还有一层工程考虑**：NFKC 有"一字符变多字符"的情况（`㍿ → 株式会社`），会平移后面所有字符的偏移，`page_of(offset)` 的页码映射全乱。手工翻译表是 1:1 替换，偏移不变，安全。

通用原则：**归一化的每一项改动，都要回答"这个改动在下游会不会造成信息损失"**。

读的时候带一条主线：**"切"是有损操作，一切以偏移可还原、引用可核对为前提**。补分隔符、不 strip、`find(g, cursor)` 定位、句子级 overlap、保守阈值——全是这条原则的具体化。

## 2.2 三种策略块数 10/10/18，为什么我看到 c47

**不是同一个口径**。notes.md 那张表来自 `/compare`：写死的内置演示文档（DEMO_PAGES）+ size=160/overlap=30 + 12 道固定问题——在这个唯一配置下，fixed 恰好 10 块、recursive 10 块、semantic 18 块。它是一次实验的**快照**，不是"语料有多少块"的统计。

而 chunk id 每次调用**从 c000 重新编号**（`id=f"c{i:03d}"`）。你看到 c47 说明那次 `/chunk` 调用切出了至少 48 块——要么把 size 滑杆调小了，要么贴了自己的长文本。

**认知坑**：块数不是策略的"属性"，是 策略 × 参数 × 文档 的三元函数。引用任何块数/recall 数字永远要带参数条件，不然就是无效对比。

## 2.3 overlap 是什么

**相邻两块之间重复携带的那段文本**。fixed 策略是滑窗：

```
size=160, overlap=30 → 步长 step=130
块0: [0, 160)
块1: [130, 290)   ← 前 30 字和块0 重复
块2: [260, 420)
```

**为什么需要**：句子、条款随时可能被切到两块里。overlap=0 时"退款申请提交后"和"3–5 个工作日内到账"分居两块，向量化后都不够"像"问题 → 丢分；overlap=30 时重叠区让边界两侧的块都保有完整上下文。它是给"跨块边界的信息"买的保险。

**代价**：块数变多（向量更多、存储更贵）；同一答案可能命中两块挤占 top_k（靠 md5 去重）；收益递减。惯例：**overlap = size 的 10%~20%**；`overlap ≥ size` 会死循环（step ≤ 0），代码直接 400 拒绝。

**fixed vs recursive 的 overlap 实现差别**：fixed 是"从尾巴数 N 个字符"复制，会切半句；recursive 是"从尾巴往回拿若干个完整原子"，重叠区永远是完整的句子/段落。

## 2.4 为什么还需要 fixed 策略（看上去全是缺点）

三重身份，缺一不可：

1. **对照组**：recall 表没有 baseline 就没有意义。"已知最笨的方法都能考 0.92，所以你的聪明方法只多 8 分"——没有 fixed，recursive 的 1.00 毫无信息量
2. **生产里真有人用**：日志/流水（无段落结构，recursive 无东西可用）、表格/JSON（结构是字段不是句子）、代码文件、超大规模语料（零模型调用、纳秒级）。另外块长绝对均匀，embedding 对块长不一致的打分不公平，均匀反而是小优点
3. **实验数据自己替它说话**：fixed 在 size=240 时 recall@3 也是 1.00。它输的不是"本质"，是"没调过参"——size=160 恰好爱切断句子，拉到 240 句子装得下，缺点消失

工程决策的正确顺序：**fixed 调参 → 不行再 recursive → 有标定条件且收益明确才 semantic**——不是上来就用最贵的。一句话：fixed 不是"差策略"，是"零成本的基准线 + 结构缺失时的兜底"。

## 2.6 语义切分的阈值为什么是 0.05

semantic 机制：49 句各变向量 → 算相邻两句余弦相似度 → **低于 threshold 就断开**。阈值不是评分标准，是切在这串数值分布上的刀——刀落在哪，取决于分布长什么样。

实测分布（本地哈希向量，49 句演示语料）：

```
0.000 ×9      ← 9 对相邻句字面重叠为零（话题断层）
0.047~0.05    ← 少数低重叠对
0.05~0.13     ← "同一话题"大部队，中位数 0.096 在这
0.15~0.38     ← 高重叠尾巴（最大 0.381）

阈值 → 块数（size=160）：
0.00→1   0.02→10   0.05→15(+size强制切=18)   0.07→18   0.12→35   0.30→48(逐句切，失效)
```

0.05 的选择逻辑：

1. **必须低于 0.096（中位数）**——大部队是"同一话题相邻句"，不能被切开
2. **必须高于 0**——9 个零重叠对是真断层，不切就会横跨话题
3. **0.02~0.04 太贴零**——和 0.05 效果差不多但无数值安全余量

所以 0.05 = "零重叠带之上、同话题主带之下"这条沟的中间位置。**0.09→0.12 块数从 22 跳到 35：中位数就是安全线**，阈值一越过它，大部队开始被成片切开。

**阈值跟模型绑定**：余弦的数值刻度是 embedder 的属性。真语义模型同语料相邻句中位数通常 0.4+，0.05 带过去会一刀都切不动（全文 1 块）；教程里 OpenAI embedding 配 0.8 拿到哈希向量上就是逐句切。正确流程永远三步：用你的语料+你的 embedder 打印分布 → 找"零/低带"和"主带"的沟 → 阈值放沟里。

## 2.7 为什么不是 0.06

0.06 和 0.05 只差 3 刀（sim 在 0.050/0.053/0.059 的句对），但这 3 刀全是错杀——实测抓出来的句对：

```
sim=0.050  "年假：入职满一年享 5 天…" / "年假需提前 3 个工作日…"   ← 同话题（年假）
sim=0.053  "所有生产数据禁止下载…" / "确需导出的，须走审批…"       ← B 是 A 的例外条款
sim=0.059  "连续病假超过 3 天…" / "迟到：每月累计迟到…"           ← 唯一勉强算换话题
```

对照零重叠组才是真断层（章节标题进正文、年假→病假、考勤→报销）。

**背后是不对称代价**：

| 错误 | 后果 | 补救 |
|---|---|---|
| 漏切（该断没断） | 块杂一点，通常还能命中 | 有兜底：`cur_len > size` 强制切 |
| 错切（同话题被分） | 语义链断，两块各自残缺 | **没有任何机制能焊回去** |

一边有兜底、一边没有，所以阈值往有兜底的那边偏——压低。完整回答：**0.06 不是不行，是严格更差**——多出的每一刀都是错杀，漏掉的有 size 兜底。原则：*切分这种没有 undo 的操作，标准要从严；块长这种有兜底的约束，可以放宽*。

## 2.8 recursive 是怎么实现的

两层结构，各管一件事：

**第 1 层 `_atoms`（"递归"两字就在这）**：拿着分隔符优先级表逐级下降：

```
SEPARATORS = ("\n\n", "\n", "。", "！", "？", "；", ". ", " ", "")
              段落      换行   句末          分号   空格   硬切(哨兵)

800 字全文, size=160
→ "\n\n" 段落级切 4 段，其中一段 300 字超长
  → 这段带着剩余阶梯递归 → "\n" 切 2 段，仍 200 字
    → 降到 "。" 句号级 → 全部 ≤160，收工
```

"递归"不是数据结构，而是：当前级别切不动（文本里没有该分隔符）就带着**剩余阶梯**降级，直到找到第一个能下刀的位置，或降到哨兵级硬切。三个易漏细节：`p + sep` 把分隔符补回去（否则拼不回原文）；`_glue_headings` 把小标题粘到正文（标题是整块最强的主题信号）；超长原子是"标题+正文"时只拆正文，标题跟走。

**第 2 层 `recursive_chunks`（贪心装箱 + overlap 回填）**：

```python
for p in pieces:
    if buf and buf_len + len(p) > size:
        grouped.append("".join(buf))     # 装不下就封箱
        keep = []
        for x in reversed(buf):          # 从箱尾往回拿完整原子
            if klen + len(x) > overlap: break
            keep.insert(0, x)
        buf = keep                        # 它们就是新箱子的开头（重叠区）
```

这是和 fixed 的本质区别：**overlap 的单位是"原子"不是"字符"**——上一箱末尾的整句/整段搬过来当下一箱开头，绝不把一句话切一半。所以 recursive 块的边界永远落在语义边界上，recall 更稳的原因就在这。

最后偏移定位用 `text.find(g, cursor)`：cursor 单调前进，保证重复文本（比如"退款政策。"出现多次）不会定位到前面去。

## 2.9 相邻句相似度：句子有多长

两层答案：

**句子的长度 = 字符数**。`sentence_spans` 的正则从一个句末标点扫到下一个（换行也算边界），每句记 `(body, start, end)`，长度 = `end - start` = `len(body)`。

**算相似度时不需要知道长度**：句子被压成固定 512 维向量，余弦又把向量长度归一掉——"句子有多长"这个信息在进入相似度计算之前就被抹掉了。

**长度唯一被用到的地方是尺寸兜底**，而且用**偏移相减**不用 len 求和：

```python
cur_len = spans[i][2] - spans[groups[-1][0]][1]
# 实测：偏移相减 108 vs len 求和 106 —— 差的是句间换行符。
# 切块按 text[s:end] 取区间，区间里含着换行；
# 用 len 求和会系统性偏小，size 上限形同虚设。
```

**隐形的间接影响**：余弦对长度免疫，但哈希 embedder 有长度敏感性——句子越短 bigram 越少，向量越稀疏，两句短句即使同话题相似度天花板也被压低。这是相邻句中位数只有 0.096 的原因之一（句子普遍 16~34 字）。真语义模型没这毛病，换模型后中位数跳到 0.4+。

## 2.10 semantic 是不是接真 embed 模型会更好

**对——semantic 就是为真语义模型设计的**。用本地哈希向量跑 semantic，等于花着语义切分的钱干字面匹配的活：它找到的"语义边界"对哈希向量根本不可见（评测数据：626 块同参数最多，recall 反而比 fixed 差）。

接真模型前想清楚三件事：

1. **成本其实不高**：切块是离线一次性操作，还能和检索共用同一批 embedding
2. **强烈建议和检索用同一个模型**：切块按"语义是否连贯"分组、检索按"语义是否相关"打分，不同模型会出现"切块认为连贯、检索不认为相关"的错位
3. **阈值必须重标**：换模型后先打印新分布（中位 0.096 → 0.4+）。更稳的做法是分位数断点（LlamaIndex 的做法：切在相似度分布最低 5% 处），比绝对阈值耐迁移

**现实障碍**：当前 `semantic_chunks` 只支持本地 embedder（同步调 `_embed_one()`；`APIEmbedder` 只有异步 `embed()`）。接真模型要改造：先批量 embed 出向量再传入——顺带一次 API 往返搞定全部句子。

什么时候值得：长文/无结构文本（转录稿、书）、话题密集文档、已用真模型检索想对齐语义空间。什么时候不值得：结构良好的文档（recursive 的阶梯已经切在真边界上）、还没配 key 的阶段。一句话：**semantic 是真模型专属策略，recursive 才是无模型时代的最优解**。

# Part 3 · 跨单元通用原则（面试素材）

1. **阈值与模型绑定**：任何作用在相似度上的阈值（语义切分 threshold、拒答 τ、过滤阈值）都刻在特定 embedder 的分数分布上。换模型 = 分布变了 = 全部重标。配套工具：每个阈值都该有一个"分布探针"（如 `_adjacent_sims`）摊开给你看，而不是瞎猜数字
2. **错切 vs 漏切的不对称代价**：没有 undo 的操作标准要从严；有兜底的约束可以放宽。这个模式在系统设计上反复出现（同样适用于缓存失效、索引重建的决策）
3. **评测口径先行**：命中 = 答案原文子串是否在前 top_k 块里（可复现、零成本、与答案正确性强相关）；rank 4~10 是"近失"（调参可救），rank 100+ 是"远失"（切块碎了）；引用任何指标必须带参数条件
4. **控制变量是实验的生命**：同一语料、同一批题、只改一个变量；12 题小样本的结论在 80 题下可能翻盘——**小样本数字只有锚点价值，没有决策价值**
5. **"切"是有损操作，偏移可还原是底线**：补分隔符、不 strip、从原文扫描偏移、1:1 归一化——全是为"引用可核对"这条 RAG 信任机制服务
6. **降级策略分场景**：教学项目配置不全要降级能跑（体验优先），生产环境必须 fail-fast（否则带着"以为在用真模型、其实在用哈希"的错误认知跑一整天实验）
