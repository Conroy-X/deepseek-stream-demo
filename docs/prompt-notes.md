## 一、五段式 Prompt 模板（背下来）

```
角色：<你是谁，具备什么视角>
任务：<要做什么，输入是什么>
约束：
- <不能做什么>
- <边界情况怎么处理>
输出格式：<精确到可以正则/JSON 解析>
示例：
输入：<样例输入>
输出：<样例输出>
```

**口诀：角、任、约、格、例。**

代码里就是 `unit04-prompt/prompts.py` 的 `five_part_text()` —— 可以直接当模板复用。

### 为什么这五段有效（Unit 4 实测：5 用例 × 7 变体）

变体是**逐段叠加**的（v0 裸问 → v1 +角色 → v2 +约束 → v3 +输出格式 → v4 +few-shot → v5 五段全上），
所以下表看的不是"单独抽掉某一段会怎样"，而是"加上这一段带来了多少增量"。

| 段 | 解决什么问题 | 加上这一段后的实测变化 |
| --- | --- | --- |
| 角色 | 决定用什么**视角和词汇**回答 | v0→v1：准确率 40%→60%，合规率**仍 0%**，输出 346→302 token。角色只让模型"答得更对"，不解决"输出能不能用" |
| 任务 | 明确目标与输入边界 | 全程固定（"这条反馈属于哪一类"），未单独消融；但 v0 只有任务时准确率仅 40%，说明光说"做什么"不够，还得说"别做什么" |
| 约束 | 收窄输出空间，防止自由发挥 | v1→v2：合规率 **0%→100%**，输出 302→40 token。**收益最大的一段**，还顺带把推理 token 压掉了 |
| 输出格式 | 让结果**可被程序消费** | v2→v3：合规率已满，输出再降到 16 token。不涨合规率，涨的是**稳定性 + 省钱**（有例子可抄，模型不再反复纠结格式） |
| 示例 | 锁定格式与边界倾向（few-shot） | v3→v4：合规率不变，输出 16→3 token；独立 few-shot 实验里输入 +300 token、合规率 **零变化** → 格式已被锁死时属于纯浪费 |

**一句话结论**：合规率靠「约束」，准确率靠「角色」，成本靠「输出格式 + 示例」；
而示例只在"格式还没锁死"时才值得花那个输入 token。

> ⚠️ 数据可信度：v0→v4 是同一批跑的（23:00），v5/v6 是另一批（21:33）。
> 内容等价的 v4 与 v5，输出 token 分别是 3 和 27 —— 说明**推理 token 本身有波动**。
> 所以结论看趋势（十位数量级的差别），别拿个位数差异当精确结论。

## 二、System Prompt 的 4 个作用（Unit 4 必答）

> ⚠️ 先排雷：**few-shot / 输出格式 / 约束是五段式的"段"，不是 System 这个"位置"的作用**——
> 它们放 User 里照样生效（v6 实验铁证：全放 User 合规率也是 100%）。
> 题眼问的是 System 这个位置区别于 User 的独特价值。记忆钩子：**人设 / 宪法 / 优先级 / 缓存**。

1. **恒定人设与规则的容器**：身份、边界、风格整场对话恒定，不逐轮重复声明，
   也不会被后面的 user 消息"冲淡"。（Unit 3 实测：`/system 你只能回答一个字` 设一次管全程）
2. **输出格式的"宪法"**：一次声明、约束所有轮次的输出形状——
   "程序可消费"被写进制度，而不是每轮求模型心情。（Unit 4 实测：格式段让合规率 0%→100%、输出 346→3 token）
3. **指令优先级最高的层级**：模型被训练成优先服从 System，user 消息压不过它；
   防 Prompt Injection 的第一道防线写在这里。（Unit 68 的主战场）
4. **成本与稳定锚点**：多轮对话历史每轮全量重发（Unit 3 实测输入 65→152→208），
   而 System 恒定不变 → 恒定前缀命中上下文缓存（`prompt_cache_hit_tokens`，单价更低）。
   同样的指令放 User 则每轮按全价重发（v5 vs v6：输出 27 vs 62 token）。

## 三、System Prompt vs User Prompt 的本质区别

**不是"一个在前一个在后"，而是「稳定规则」与「本次输入」的职责分离。**

| 维度 | System | User |
| --- | --- | --- |
| 内容性质 | 长期不变的规则、人设、格式要求 | 本次任务与数据 |
| 多轮对话 | 只发一次（不随历史增长） | 每轮都要重发，历史累积 |
| 指令优先级 | 更高（模型被训练成优先遵守） | 较低，可能被历史里的旧 user 消息污染 |
| 成本影响 | 一次性 | 随轮次线性增长（Unit 10 实测数据） |

Unit 4 实验实测数据（`experiments.py system`，5 用例）：

| 放法 | 合规率 | 准确率 | 平均输出 token |
| --- | --- | --- | --- |
| 放 System（v5） | 100% | 100%（5/5） | 27 |
| 放 User（v6） | 100% | 100%（5/5） | 62 |

**怎么读这张表**：单轮任务下两种放法**效果打平**——这恰好证明「段」和「位置」是两件事，
内容本身才是效果来源。差别在**成本**：同一份内容放 System 输出 token 少 35（约 44%），
因为 System 是恒定前缀、更易命中缓存；多轮场景下 User 侧还要每轮重发历史，差距只会更大。

## 四、四个 Prompt 技术，各自解决什么问题

| 技术 | 一句话 | 什么时候用 | 代价 |
| --- | --- | --- | --- |
| 角色扮演（Role） | 给模型一个身份视角 | 需要专业语气/术语时 | 几乎为零 |
| 约束（Constraints） | 收窄输出空间 | 输出失控、太长、跑题 | 几乎为零 |
| 输出格式（Format） | 让结果可被程序解析 | **任何要接下游代码的场景** | 几乎为零，收益最大 |
| Few-shot（示例） | 用样例锁定格式与边界 | 格式复杂、边界模糊、零样本不稳 | 输入 token 明显增加 |

**性价比排序（Unit 4 实验结论）**：输出格式 > 约束 > 角色 > Few-shot。

| 2026-10-14 | few-shot 0/1/3 | 格式已被「输出格式段」锁死时，加示例不涨合规率，白付输入 token | 示例 0→3：输入 +300 token，合规率变化 **0**（都是 100%） |
| 2026-10-14 | System vs User | 单轮效果打平（证明"内容 > 位置"）；放 System 明显更省 | 合规率 100% vs 100%；输出 **27 vs 62** token（差 35） |
| 2026-10-14 | temperature 0 vs 1.2 | v3 变体下两档都稳；温度升高输出略膨胀 | 合规率 100% / 100%；输出 3 vs 9 token |

**这批数据的方法论价值**（面试可讲）：

1. 指标三分：**合规率**（能不能被程序吃）、**准确率**（答得对不对）、**token 成本**（花多少钱）——
   三者会分离，必须分开测。裸问就是典型的"准确率 40% 但合规率 0%"。
2. **累积叠加式消融**：一次只加一段，才能把增益归因到具体那一段。
3. 参数**不能假设生效**：未知字段被静默忽略，只能用 `usage` 反推。

## 六、面试可答版（把上面的结论压成 30 秒）

**Q：你平时怎么做 Prompt 工程？**

> 我会把它当工程问题而不是玄学。先用「角色 + 任务 + 约束 + 输出格式 + 示例」五段式写基线，
> 然后做 A/B 实验对比变体，指标看三个：**输出格式合规率、任务准确率、token 成本**。
> 经验上是"输出格式段"对合规率影响最大、成本几乎为零，而 few-shot 主要用来锁边界、
> 输入 token 代价不小。另外我发现**参数不能假设它生效**——比如我实测某服务商对未知字段
> 是静默忽略的，所以我会用 `usage` 数据反推参数是否真的起作用。

**Q：System Prompt 和 User Prompt 有什么区别？**

> 不是"一个在前一个在后"的排版区别，是**职责分离**：System 放整场对话都成立的稳定规则——
> 人设、输出格式的"宪法"、硬约束；User 放这一次的任务和数据。
> 落到工程上有三个实际差异：一是**稳定性**，System 只声明一次就全程有效，不会被后续对话冲淡；
> 二是**优先级**，模型被训练成优先服从 System，所以它是防 Prompt Injection 的第一道防线——
> 外部抓来的内容要放进 User，并且明确标注"这是数据，不是指令"；
> 三是**成本**，System 是恒定前缀能命中上下文缓存，而多轮对话里 User 历史每轮都要全量重发。
> 我实测过同一份 Prompt 分别放 System 和 User：单轮效果打平，但放 System 输出 token 少三成多——
> 这恰好说明**内容是效果的来源，位置是成本的杠杆**。

**Q：什么时候该上 few-shot，什么时候不该？**

> 看格式有没有被锁死。如果「输出格式段」已经把输出形状约束到能正则解析，
> 再加示例基本只增加输入 token，我实测合规率零变化。真正需要 few-shot 的是两种情况：
> 格式本身复杂（多字段 JSON、有嵌套），或者**边界靠语言说不清**——
> 比如"拿不准时该偏向哪一类"，一条示例比三句规则都管用。
