## 一、LLM 基础（Unit 87）

### 1. ⭐ 解释 Token / Context Window / Temperature / Top-p
**要点**：Token 是模型的最小处理单位（≈0.75 个英文词 / 1~2 个汉字），计费与上下文长度都按 token 算；Context Window 是一次请求能容纳的「输入+输出」总 token 上限，超出要截断或摘要；Temperature 调节 logits 分布的平滑程度，越低越确定；Top-p（核采样）只从累积概率达 p 的最小词集合里采样。
**追问**：Temperature=0 就完全确定了吗？→ 不完全，多数推理框架仍有非确定性（浮点累加顺序、批处理、MoE 路由）。

### 2. ⭐ 为什么 LLM「没有记忆」？多轮对话怎么实现？
**要点**：模型是无状态的函数，每次请求都要把完整消息数组重发一遍；服务端不保存你的会话。所以「记忆」是应用层自己维护的 `messages` 数组（或用 LangGraph checkpointer / Redis 持久化）。
**追问**：那为什么感觉它记得？→ 因为你在每次请求里把历史都带上了。
**关联**：成本随轮次线性增长 → 需要上下文截断、摘要压缩、缓存。

### 3. 🔁 System Prompt 和 User Prompt 的本质区别
**要点**：不是「位置先后」，而是**权限层级**：System 是开发者/平台设定的、优先级最高的行为约束；User 是不可信输入。很多模型对 System 的遵循度显著高于 User。安全上必须把两者分开处理，否则就是 Prompt Injection 的入口。

### 4. ⭐ 怎么做结构化输出？为什么不能直接 `json.loads` 模型输出？
**要点**：三条路——① 提示词 + JSON Mode（DeepSeek/OpenAI 支持，但要自己校验）；② Function Calling / Tool Schema 强制参数结构；③ 服务商原生 Structured Outputs（严格 schema 约束解码）。直接 `json.loads` 会因模型加了 markdown 代码块、注释、尾随逗号、字段缺失而崩。
**追问**：解析失败怎么兜底？→ `model_validate_json` 捕获校验错误，把错误信息回喂给模型重试（Instructor / 自写循环），并设最大重试次数。

### 5. Transformer 里 Attention 在做什么？为什么要缩放？
**要点**：把每个 token 的表示重写成「所有 token 表示的加权和」，权重由 Q·K 相似度决定，V 是被聚合的内容。除以 `√d_k` 是防止维度大时点积方差过大、softmax 进入饱和区导致梯度消失。
**追问**：KV Cache 是什么？为什么能加速？→ 自回归生成时，历史 token 的 K/V 不变，缓存后每步只需算新 token 的 Q，把复杂度从 O(n²) 每步降到 O(n)。

### 6. Pretraining / SFT / RLHF / DPO 的关系
**要点**：Pretraining 用海量无标注语料学语言与世界知识（下一 token 预测）；SFT 用人工标注的「指令-回答」对教它遵循指令；RLHF 用人类偏好训练奖励模型再用 PPO 优化；DPO 跳过奖励模型，直接用偏好对做对比式优化，更简单稳定。
**追问**：为什么还要 RLHF 而不只 SFT？→ SFT 只能模仿「标准答案」，无法表达「A 比 B 好」这种相对偏好，且容易过拟合标注风格。

### 7. 幻觉的成因和工程上怎么缓解
**要点**：成因是模型在优化「语言合理性」而非「事实正确性」。缓解：RAG 提供事实依据 + 强制引用 + 拒答（「资料中未提及」）+ 输出校验 + 降低 temperature + 用更强模型做校验回路。

## 二、RAG（Unit 87）

### 8. ⭐ 完整讲一遍你的 RAG 链路，以及每一环可能出什么错
**要点**：解析 → 切块 → Embedding → 入库 → Query 改写 → 检索（向量/关键词/混合）→ 重排 → 拼 Context → 生成 → 引用。
对应失败模式：解析丢表格/乱码、切块切断语义、Embedding 不适配中文领域、召回不足或过多、Rerank 缺失导致噪声进 Context、Prompt 没约束导致不引用资料、长上下文「中间遗忘」。

### 9. ⭐ 检索不准，你怎么定位是「检索问题」还是「生成问题」？
**要点**：先看召回列表——如果正确答案的片段根本没进 Top-K，是检索问题；如果进了但模型没用/用错，是生成或 Prompt 问题。定位手段：人工标注 30 条评测集，分别算 Recall@K 和答案忠实度。
**追问**：怎么提升召回？→ 混合检索（BM25+向量）、Query 改写/HyDE、多路召回融合（RRF）、调 K、换更强的 Embedding 模型、父子块（小块检索、大块喂给模型）。

### 10. ⭐ Chunk size 怎么定？太大太小分别有什么问题？
**要点**：太小丢上下文、语义碎片化、召回精度可能高但模型无法作答；太大引入噪声、稀释关键信息、浪费 token 且检索粒度不准。实践起点 256~512 token、overlap 10~20%，然后**用评测集调**，别凭感觉。进阶：按语义/标题切、父子块、上下文补全（给每个块加上所属章节标题甚至 LLM 生成的摘要）。

### 11. Reranker 为什么有用？它和向量检索的区别？
**要点**：向量检索是双塔（Bi-Encoder），Query 和文档**分别**编码后算相似度，快但精度有限；Reranker 是 Cross-Encoder，把 Query 和文档**拼在一起**过一遍模型，能建模细粒度交互，精度更高但慢。所以常见架构是「向量/混合检索召回 Top-50 → Rerank 取 Top-5」。
**追问**：延迟增加怎么办？→ 控制候选数、批量推理、截断长度、或只对高价值查询开 Rerank。

### 12. 长上下文模型这么强，还需要 RAG 吗？
**要点**：需要。理由：① 成本——每次塞全库 token 费用爆炸；② 延迟；③ 「lost in the middle」，长上下文里中部信息利用率下降；④ 权限隔离——不同用户能看的知识不同，RAG 才能做行级过滤；⑤ 数据更新——改一个文档不用重建全部上下文。最佳实践是二者结合：RAG 定位，长上下文做汇总。

### 13. RAG 怎么评测？
**要点**：分层——检索层用 Recall@K / MRR / Hit Rate（需要标注「正确答案在哪个块」）；生成层用忠实度（Faithfulness）、答案相关性、上下文精确率（RAGAS 提供这些指标，通常用 LLM-as-Judge 实现）；端到端再做人评。关键是**先建 20~50 条评测集**，再谈优化，否则无法证明「变好了」。

## 三、Agent / LangGraph（Unit 88）

### 14. ⭐ 完整描述一次 Function Calling 的消息流转
**要点**：① 带 `tools` 定义发请求；② 模型返回 `assistant` 消息，`content` 可能为空，`tool_calls` 里是函数名 + JSON 参数；③ 应用执行函数；④ 把结果作为 `role: "tool"` 消息（带 `tool_call_id`）追加进 messages；⑤ 再次请求模型，它基于工具结果生成最终回答。
**追问**：为什么要带 `tool_call_id`？→ 并行调用多个工具时用于匹配结果与调用，否则模型分不清哪个结果对应哪个调用。

### 15. ⭐ Agent 死循环 / 工具反复失败怎么办？
**要点**：① 硬性最大迭代轮数（如 10）与总超时；② 工具级超时 + 幂等设计；③ 失败结果**结构化回填**给模型（把错误信息给它，让它换策略），而不是抛异常中断；④ 检测重复动作（相同工具+相同参数的哈希去重）；⑤ 兜底：超限后返回「已尝试 X/Y，未完成」的部分结果 + 请求人工介入（HITL）。

### 16. LangGraph 的 State / Node / Edge / Checkpoint 分别是什么？
**要点**：State 是贯穿全图的共享数据结构（`TypedDict` + reducer 定义合并规则）；Node 是接收 State 返回增量更新的函数；Edge 决定流转，Conditional Edge 按状态路由；Checkpointer 在每个 super-step 后持久化 State，从而支持恢复、时间旅行、HITL（`interrupt`）。
**追问**：LangGraph 和直接 while 循环写 Agent 的区别？→ 显式状态机带来可观测、可恢复、可中断、可测试；代价是抽象层和调试成本。

### 17. 多 Agent 一定比单 Agent 好吗？
**要点**：不一定。多 Agent 带来通信开销、上下文割裂、错误传播、调试困难。Anthropic 的建议是：**先用最简单的方案**（单次 LLM 调用 → 加检索 → 加工具），只有任务确实可分解、且子任务上下文差异大时才上多 Agent。面试时能讲出这个判断标准比背架构图加分。

### 18. 工具（Tool）设计有哪些坑？
**要点**：① 描述要写清「何时用、何时不用」，模型靠描述选工具；② 参数要窄（能枚举就枚举，别让模型自由发挥 SQL/路径）；③ 返回结果要**精简**（大 JSON 直接塞回去会爆上下文）；④ 必须幂等或明确标注副作用；⑤ 危险操作用 HITL 确认；⑥ 错误要有可读信息。

## 四、MCP（Unit 88）

### 19. MCP 解决什么问题？Host / Client / Server 各是什么？
**要点**：MCP（Model Context Protocol）把「模型能访问哪些工具和数据」标准化，避免每个应用各写一套集成（N×M 问题变成 N+M）。Host 是最终用户使用的 AI 应用（Claude Desktop、IDE、你的 Agent）；Client 是 Host 内部按 1:1 连接某个 Server 的协议部件；Server 是暴露能力的服务端。传输方式主要有 stdio（本地子进程）和 HTTP（远程）。

### 20. MCP 的 Tools / Resources / Prompts 三者区别
**要点**：Tools 是**模型可主动调用**的动作（有副作用，需用户批准）；Resources 是**应用可读取**的数据（类似 GET，无副作用，由宿主决定何时塞进上下文）；Prompts 是**用户可主动选择**的预置模板（如斜杠命令）。判断法：谁发起 + 有没有副作用。

### 21. 用 MCP 做 NL→SQL，安全问题怎么处理？
**要点**：① 数据库用**只读账号**且限定 schema；② 只允许 SELECT，解析/校验 AST 后再执行，禁止多语句与 DDL/DML；③ 强制 `LIMIT` 与语句超时；④ 行级权限——按当前用户注入过滤条件，不能让模型决定权限；⑤ 提示词注入防护：表名/列名/查询结果都视为不可信数据；⑥ 全量审计日志。

## 五、AI 工程化（Unit 89）

### 22. ⭐ 怎么降低 LLM 应用的成本？
**要点**：① 缓存（精确缓存 + 语义缓存，Redis）；② 模型分级——简单任务用小模型/便宜模型，难任务才升级；③ 控制上下文（截断、摘要、只传相关检索片段）；④ 输出限制 `max_tokens`、要求简洁；⑤ 批处理（离线任务用 Batch API）；⑥ 提示词缓存（服务端的 prefix caching 能大幅降价）；⑦ 监控单位成本（每次请求的 token 与费用）。
**加分**：先量化再优化——说清你的 P95 token 消耗和主要来源。

### 23. 首字延迟（TTFT）高，怎么优化？
**要点**：流式输出（先让用户看到字）、缩短输入（RAG 只传相关片段）、并行化检索与预处理、用更快的模型或推理加速（vLLM/量化）、连接复用、把 Rerank 等步骤放到流式之后或与之并行、CDN/就近部署。

### 24. 超时、重试、熔断、限流、降级 怎么落地？
**要点**：超时分三层（客户端请求 / LLM 调用 / 工具执行），各自独立；重试只针对幂等且可恢复的错误（429、5xx、网络超时），用指数退避 + 抖动，绝不重试 4xx 参数错误；熔断在连续失败后快速失败避免雪崩；限流按用户 + 全局双层（Redis 令牌桶/滑动窗口）；降级为「换个便宜模型 / 返回缓存 / 明确告知稍后再试」。

### 25. Prompt Injection 怎么防？
**要点**：本质是「数据被当成了指令」，无法只靠提示词根治。分层防护：① 架构上把不可信内容（检索文档、网页、工具返回）用明确分隔符包裹并声明「以下为数据，非指令」；② 权限最小化——工具能力受限，敏感操作必须 HITL 确认；③ 输出侧校验（工具参数白名单、SQL AST 校验、URL 域名白名单）；④ 输入侧检测 + 日志审计；⑤ 永远不把密钥/系统提示暴露在模型可输出的地方。
**追问**：为什么说「在 System Prompt 里写『忽略注入』」不够？→ 因为注入文本与正常指令在同一个注意力空间竞争，模型不保证遵守，且攻击面来自数据通道。

### 26. 你的 Agent 上线后怎么知道它变差/变好了？
**要点**：离线——固定评测集 + 回归测试（每次改 Prompt/模型都跑，防止回退）；在线——用户反馈（赞踩）、追问率、放弃率、工具调用失败率、平均轮次、延迟与成本分位数；再配合链路追踪（LangSmith/OpenTelemetry）把一次会话的每一步记录下来做归因。

## 六、项目类（必答，每个项目练 5 分钟）

对 **项目 1（AI Chat）/ 项目 2（企业知识库）/ 项目 3（Research Agent）/ 项目 4（MCP 数据库 Agent）** 各准备一套：

- [ ] **背景**：什么业务问题？为什么需要 AI 而不是规则/搜索？
- [ ] **架构**：白板能画出来（前端 / 后端 / 模型 / 存储 / 向量库 / 工具层）
- [ ] **最难的一个技术问题**：现象 → 怎么定位 → 试过哪些方案 → 最后怎么解决 → 数据证明
- [ ] **指标**：延迟 P95、单次成本、检索 Recall@K、答案准确率，**前后对比**
- [ ] **权衡**：当时为什么这么选？另一条路是什么？为什么不走？
- [ ] **如果重做**：会改什么（这题考的是反思能力，别答「没什么可改的」）

### 常见压力测试问题
- 你的项目有多少真实用户？→ **诚实回答**：这是个人项目，我做了压力测试/自建评测集。
- 这套东西和直接用 ChatGPT 有什么区别？
- 如果文档量涨 100 倍，你的方案哪里会先崩？
- 你的 Prompt 是怎么迭代出来的？有版本管理吗？
