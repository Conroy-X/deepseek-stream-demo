> 重点是：**这三样东西为什么不是一回事。**

## 本次做了什么

  `classify()` 挑刺器、11 个样例帧。

## 一、为什么它们不是并列关系

网上很多文章会画三个方框并排放，然后说「MCP 提供三种能力」。这让人以为可以随便挑一个放进去。
实际上三条能力分布在一条**控制轴**上：

| 能力 | 谁决定 | 怎么触发 | 副作用 | 放错的后果 |
| --- | --- | --- | --- | --- |
| Tools | **模型** | 模型在对话里自己判断该不该调 | 允许（这正是它的价值） | 只读操作用户不知道有，模型也永远不会调 |
| Resources | **应用（宿主）** | 宿主 UI 勾选 / 自动挂载上下文 | **不该有** | 写操作被自动挂载，绕过用户确认 |
| Prompts | **用户** | 用户显式选模板（类斜杠命令） | 无 | 用户得先知道有这个东西才能用 |

这条轴决定了一切后续设计：权限模型、UI 摆在哪、能不能有副作用、要不要确认。

## 二、一个需求，三种做法

需求：**让模型能读到《请假制度》全文。**

做成 tool：`get_leave_doc() → 全文`。
问题是模型**不知道这份文档存在**。它得先恰好调了 `tools/list`、恰好读懂了描述、
恰好判断此刻该读 —— 三个恰好。实际上它永远不会调。

做成 resource：`doc://handbook/leave`。
宿主在资源面板里摆放出来，用户勾选或按规则自动挂载，模型看到的就是一段现成上下文。
**不需要「想到去拿」**，这才是 resource 存在的理由。

做成 prompt：`summarize(text=...)`。
prompt 只产出消息，不产出内容。用户得先有原文才能用 —— 这里恰恰拿不到原文。

所以「读文档」这件事，只有 resource 是对的。这个判断不是审美，是控制轴推出来的。

## 三、URI 模板：resource 唯一需要解析的地方

tool 的参数用 JSON Schema 描述，resource 的「参数」被塞进了 URI ——
因为 resource 的身份就是一个地址。于是有了模板：

```
doc://kb/{topic}    →    doc://kb/expense    →    {"topic": "expense"}
```

两个实现细节：

- **字面量必须 `re.escape`**。`doc://` 里的 `.` 是正则元字符，不转义会匹配到 `docX//`。
  自检里专门有一条 `two.match("docX//kb/expense/v2") is None`。
- **`[^/]+` 而不是 `.+`**。否则 `doc://kb/a/b` 也会命中单变量模板，把两段路径塞进一个参数。

第一版我把 `__init__` 写了两遍（先 escape 再 sub，又 sub 回来），逻辑互相覆盖。
正确写法是 `re.split` 按占位符切开，奇数位放 `([^/]+)`、偶数位 `re.escape`。

## 四、`-32601` 不是「拒绝」，是「没有」

把能力表裁到只剩 `tools`，再调 `resources/list`：

```json
{"jsonrpc":"2.0","id":2,"error":{"code":-32601,"message":"Method not found: resources/list",
 "data":{"declared":["tools"]}}}
```

这个区别很实用：客户端收到 `-32601`，就知道**不该在 UI 上显示资源面板**；
如果是「有但你没权限」，才需要提示权限。搞混了会做出「点了才知道不能用」的界面。

也解释了为什么 `data` 要带 `declared` —— 报错要给出路，而不是只说「不行」。

## 五、注解：给宿主的确认策略用

```python
annotations={"readOnlyHint": False, "destructiveHint": True, "idempotentHint": False}
```

这三个 hint 不是给模型看的，是给**宿主**看的 —— 宿主据此决定要不要弹确认框。
所以写错注解的真实后果是：一件会扣库存的事被当成只读操作，静默执行了。

自检里断言了「写操作必须声明 `destructiveHint: true` 且 `readOnlyHint: false`」，
以及「两者不能同时为 true」。

## 六、挑刺器：把「别扭」变成可检查的规则

放错格子**不会报错**。这才是最麻烦的地方 —— 代码全绿，用起来就是不对。
所以我写了 `classify()`，把三种凭直觉容易放错的情况变成规则：

| 规则码 | 触发条件 | 建议 |
| --- | --- | --- |
| `READONLY_TOOL_LOOKS_LIKE_RESOURCE` | tool + `readOnlyHint: true` + 名字是读动词 | 改 resource |
| `SIDE_EFFECT_IN_RESOURCE` | resource + 名字是写动词 | 改 tool |
| `PROMPT_LOOKS_LIKE_CAPABILITY` | prompt + 名字是动词 | 名字改成描述产出 |
| `CONTRADICTORY_ANNOTATIONS` | `readOnlyHint` 与 `destructiveHint` 同时 true | 修注解 |

实测 5 条样例挑出 4 条，**正常的写操作工具不误报** —— 最后这条比挑出 4 条更重要：
一个什么都要报警的 linter 等于没有 linter。

## 七、两个容易写错的返回形状

- `resources/templates/list` 的字段是 `resourceTemplates`，不是 `templates`；
  每项字段是 `uriTemplate`，不是 `uri`。混用会让客户端解析不出来。
- `prompts/get` 返回 `messages` 数组（`role` + `content.text`），**不是字符串**。
  因为一个模板可能产出多轮消息（system 预设 + user 内容）。返回字符串的 server 在不少宿主上直接不工作。

## 完成标准对照

| 标准 | 达成情况 |
| --- | --- |
| 说清三条控制轴 | `CONTROL_AXIS` 四种 owner 断言、`owner` 两两不同 |
| 解释 read 该做成 resource | `/api/three-ways` 三种做法对比，自检确认只有 resource 合适 |
| 说清没声明能力时发生什么 | 裁剪接口实测 `-32601`，且 `tools` 仍可用 |
| 三类能力都能跑 | tools 调用真扣库存（42→40）、resource 读两次一致、prompt 必填与默认值都验 |
| 离线可自检 | 97 条断言，0 失败，连跑两次一致，无 SDK、无网络 |

## 一句话总结

**能力分类不是名词问题，是「谁有权决定」的问题 —— 决定权在哪一层，它就该是哪一种能力。**

## 面试追问

**Q：什么情况下一个只读功能也该做成 tool，而不是 resource？**
A：当它**需要参数且参数是活的**时。resource 的「参数」只能进 URI，适合「按名字取一份确定的东西」；
如果用户（或模型）需要传类似「过去 7 天、按地区聚合」这种结构化查询，URI 装不下，
而模型必须能自己决定要不要查、查什么 —— 那就该是 tool。
判据是：**谁需要决定「取哪一份」**。宿主能预先枚举出来的 → resource；模型临场决定的 → tool。

**Q：prompt 和 system prompt 有什么区别？**
A：system prompt 是**你的应用**在每次请求里固定注入的；MCP 的 prompt 是**用户**显式选择的一段模板。
区别在控制权：前者你说了算、用户看不见；后者用户点了才会进对话，本质上是「可复用的输入片段」。
所以 prompt 适合放「用户会反复用的任务模板」（总结、审查、翻译），不适合放「行为约束」。

**Q：为什么 MCP 不把 resource 也做成 tool 调用？**
A：因为**上下文和动作是两种不同的东西，混在一起会丢信息**。
上下文是可以预取的、可以缓存、可以整批挂载的，客户端能提前准备好；
动作必须由模型临场决定。如果全做成 tool，客户端就没法「提前把相关文档挂上」，
只能等工作流跑到那一步再去拿 —— 而模型不知道自己该去拿。
一旦两者混为一种，客户端就失去了「预取」和「枚举」这两个能力。

**Q：注解（annotations）能不能当安全边界？**
A：不能。注解只是**提示**，服务端想写什么写什么，客户端也不保证遵守。
真正的安全边界在执行侧：只读连接、白名单、权限校验。
注解的用途是让宿主决定**要不要弹确认框**，是 UX 层面的事，
把它当成权限控制就等着出事。
