## 本次做了什么

- 设计 `Conversation 1—N Message` 两张表，SQLite 持久化

- 关键顺序：**先把用户消息落库，再调模型**

## 数据模型

```
Conversation 1 ──── N Message
```

### 四个设计决定

| 决定 | 理由 |
| --- | --- |
| 存完整历史，不只存最后一条 | LLM 无状态，每轮都要重发全部历史 |
| `role` 加 `CHECK` 约束 | 写错成 `robot` 不会报错但行为异常，数据库层拦住最可靠 |
| `ON DELETE CASCADE` | 否则删会话后 messages 变孤儿数据 |
| 按 `id` 排序而非 `created_at` | 同秒插入时 `created_at` 顺序不确定，`id` 严格递增 |

### 索引

```sql
CREATE INDEX idx_msg_conv ON messages(conversation_id, created_at);
```

查询「某会话的全部消息」走这个索引，避免全表扫描。

## 为什么不能只存最后一条消息

**这是本单元的核心问题，面试高频。**

LLM 本身**没有记忆**。所谓「多轮对话」是应用层每次把完整历史重新发一遍：

```
第 1 轮请求： [system][user:我叫张三]
第 2 轮请求： [system][user:我叫张三][assistant:你好张三][user:我叫什么?]
```

如果只存最后一条，第 2 轮就只有 `[user:我叫什么?]`，模型当然答不出来。

## 为什么先落库再调模型

```
❌ 先调模型，成功后一起存 → 模型报错时用户的话丢了
✅ 先存 user 消息，再调模型 → 无论成败，用户输入都在
```

实测验证过：缺 Key 时请求失败，但用户消息已经在数据库里了。

## 面试追问

**Q: 为什么用 SQLite？**
> 学习阶段零配置、零依赖，单文件好备份。局限是并发写会锁表、无用户概念。
> 生产要换 PostgreSQL（Unit 11）。

**Q: 会话多了怎么优化列表查询？**
> 当前用子查询算 `msg_count`。数据量大时应该：①给 `conversations.updated_at` 加索引
> ②把消息数冗余存到 `conversations` 表 ③列表分页。

**Q: 历史很长怎么办？**
> 这正是 Unit 10 要解决的。当前是全量发送，会撑爆上下文窗口。

**Q: 怎么保证消息顺序？**
> 按 `id`（自增主键）排序，而不是 `created_at`。
> 因为 `created_at` 是浮点秒，同一秒内插入多条时顺序不确定。
