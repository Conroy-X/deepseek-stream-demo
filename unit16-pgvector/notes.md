### Q1 · HNSW 和 IVFFlat 的区别与取舍

| 维度 | HNSW | IVFFlat |
| --- | --- | --- |
| 结构 | **多层邻近图**：上层稀疏做粗定位，下层稠密做精查，查询从顶层往下逐层收敛 | **倒排桶**：先 k-means 把向量聚成 `lists` 个簇，查询时只扫离查询最近的 `probes` 个桶 |
| 建索引要不要先有数据 | **不要**，空表也能建，插入时增量维护图 | **要**。空表建出来是废索引（聚类中心退化），之后灌满数据也不会自动重聚类，得 `REINDEX` |
| 参数 | `m`（每节点边数，默认 16）、`ef_construction`（建图候选集，默认 64）、查询时 `ef_search`（默认 40） | `lists`（桶数，经验 `rows/1000`，≤1M 行）、查询时 `probes`（默认 1） |
| 内存 | 吃得多：图 + 向量常驻 | 吃得少：只多聚类中心和桶内 id |
| 插入新数据 | 直接插，增量更新图，质量略降 | 能插，但会落进已有簇；**大量新增后分布漂移，必须 REINDEX** |
| 建索引速度 | 慢（本机 5 万行 57.7s） | 快（本机 5 万行 15.7s） |
| 查询速度 | 极快（5 万行 0.3ms） | 快但受 `probes` 影响（5 万行 4.4ms） |
| 召回 100%？ | 不能，`ef_search` 太小时必漏（实测 ef=1 → recall 0.10） | 不能，`probes < lists` 时可能漏桶 |

**取舍一句话**：写入频繁、要召回、能接受内存和建索引成本 → **HNSW**；
数据相对静态、内存吃紧、能接受周期性重建 → **IVFFlat**；
数据量不大 → **不建**（见 Q2）。

### Q2 · 什么时候**不该**建索引

先算体积：

```
5 万条 × 512 维 × 4 字节 ≈ 102 MB 原始向量（加索引和行开销，本机实测整表 150 MB）
```

再看本机实测：5 万行全表扫 **144 ms**；1 万行 **26.7 ms**；1 千行 **2.8 ms**。

也就是说：**1 万条以内，全表扫就够快**（20 多毫秒，用户感知不到）。
而 HNSW 建一次要 3.4s（1 万行）/ 57.7s（5 万行）、常驻内存、每次插入还要维护图。
QPS 不高时（内部知识库、后台工具），这笔买卖不划算。

**面试变体**：「1 万条数据要不要上 pgvector 索引？」
答"要，索引快"是错的。正确回答：
「先看数据量和维度：1 万条 × 768 维约 30MB，全表扫 10–30ms，够用就不建。
真建了，小表上 planner 可能直接无视索引（本机 1 万行 IVFFlat 就是 Seq Scan 26ms），
白付了建索引和内存的成本。等数据过十万、或 p95 延迟成为瓶颈再上 HNSW；
而且索引是近似检索，有召回损失，小数据量精确检索反而更准。」

一句话：**索引解决的是"数据量 × 维度大到顺序扫描不可接受"，不是"让查询变快"的万能药。**

### Q3 · `<=>`、`<#>`、`<->` 分别是什么

| 算子 | 含义 | 需要先归一化吗 |
| --- | --- | --- |
| `<=>` | **余弦距离** = `1 - cos(a,b)`，范围 [0,2] | 不强制，但归一化后它等于内积距离，且能直接用 `vector_cosine_ops` 索引 |
| `<#>` | **负内积** = `-(a·b)` | **强烈建议**。不归一化时内积偏袒长向量（模长大的相似度虚高） |
| `<->` | **欧氏距离**（L2） | 不强制；归一化后 `d² = 2 - 2cos`，与 `<=>` 单调等价 |

**Unit 15 的归一化对哪个有影响？** 三个都有，但道理不同：

- `<=>`：本来不受模长影响，归一化只是让"距离 = 1 - 内积"
- `<#>`：**影响最大**。未归一化时 `a·b` 被长度放大，长文本天然占优；归一化后 `-内积 = -cos` 才和余弦等价
- `<->`：归一化后与余弦单调等价 —— 排序结果一样，但**必须配 `vector_l2_ops` 索引**，ops 不匹配索引不生效

## 实测数据

环境：WSL2 / PostgreSQL 17.11 / pgvector 0.8.0 / 512 维聚类向量（200 簇，同簇余弦≈0.89）/ `top_k=10` / 5 次取中位数。
（`uv run python bench.py` 可复现）

| 数据量 | 无索引 | HNSW | IVFFlat | 建 HNSW | 建 IVFFlat | recall@10 HNSW / IVFFlat |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 2.8 ms | 0.5 ms | 0.4 ms | 0.3s | 0.2s | 1.00 / 1.00 |
| 10,000 | 26.7 ms | 0.2 ms | 26.0 ms | 3.4s | 0.7s | 1.00 / 1.00 |
| 50,000 | 144.0 ms | 0.3 ms | 4.4 ms | 57.7s | 15.7s | 1.00 / 1.00 |

三个必须看懂的格子：

1. **1 万行 IVFFlat 是 26.0ms 且计划是 Seq Scan** —— 索引建了但 planner 不用它（`lists=10` 太粗，走索引不划算）。
   **建了索引 ≠ 用上索引，一定要 EXPLAIN 确认。**
2. **1 千行三种方式都在 3ms 以内** —— 这个规模索引没意义，直接全扫。
3. **recall 全是 1.00** —— 不是"索引精确"，是这批数据簇结构清晰、默认参数够用。往下压参数就会漏。

### 参数取舍（`sweep.py`，5 万行）

HNSW（`m=16, ef_construction=64`）：

| ef_search | P50 延迟 | recall@10 |
| --- | --- | --- |
| 1 | 0.62 ms | **0.10** |
| 4 | 0.66 ms | 0.40 |
| 10 | 0.69 ms | 1.00 |
| 40（默认） | 0.74 ms | 1.00 |
| 100 | 0.84 ms | 1.00 |
| 200 | **193.76 ms** | 1.00 |

IVFFlat（`lists=50`）：

| probes | P50 延迟 | recall@10 |
| --- | --- | --- |
| 1（默认） | 1.01 ms | 1.00 |
| 2 | 1.28 ms | 1.00 |
| 5 | 3.49 ms | 1.00 |
| 10 | 5.88 ms | 1.00 |
| 25 / 50 | ~150 ms | 1.00 |

**最后一行是最值钱的发现**：`ef_search` 调到 200，你以为能提高召回，结果
planner 认为"走 HNSW 太贵"，直接退回 `Seq Scan + Sort` —— 延迟从 0.84ms 变成 193.76ms。
用 `EXPLAIN` 看过才发现的，光看延迟会以为"索引调参调崩了"。
IVFFlat 的 `probes` 25/50 同理。

**结论**：`ef_search` / `probes` 不是越大越好，存在一个"超了就被 planner 抛弃"的拐点。
真实项目里先 EXPLAIN 确认走索引，再谈调参。

## 造数踩的坑：为什么数据分布决定索引能不能用

这一节是这一单元最有价值的私货，两版数据都翻过车：

**第一版用纯随机向量** → HNSW recall 只有 0.10。
不是索引坏：512 维里两个随机向量几乎正交（余弦标准差约 1/√512 ≈ 0.044），
**所有点彼此等距**，"找最近的 10 个"本身是病态问题，任何图索引都失效。

**第二版用了簇心 + 噪声，但把簇心归一化了** → 同簇余弦只有 0.013，等于还是随机。
原因：归一化后簇心模长 = 1，而噪声（每维 std 0.35，512 维）模长 ≈ 7.9 —— **噪声比簇心大 8 倍**。
修法是簇心保持标准正态（模长 ≈ √512 ≈ 22.6），只在采样后统归一化。修完同簇余弦 0.89、簇间 0.00。

**教训**：做向量检索的评测/压测，先验一件事——**你的数据到底有没有"近邻结构"**。
没有的话，测出来的召回率毫无意义，换成真实 embedding（bge-m3 之类）也不会是这个数字。
`bench.py` 里留了那段注释当路标，下次别再踩。

## 四个实现细节（都是坑）

### 1. Python list 不能直接塞进 vector 列

psycopg 会把 list 适配成 `float8[]`，vector 列不收：

```
column "emb" is of type vector but expression is of type double precision[]
```

解法：转成 `'[0.1,0.2,...]'` 字符串 + `CAST(:e AS vector)`（本单元用的），
或 `pgvector` 包的 `register_vector`（更优雅，但多一层隐式转换，出问题时看不见实际 SQL）。

### 2. `ORDER BY 距离` 而不是 `ORDER BY 分数`

```sql
-- ✅ 能走索引：按索引的有序距离取前 K
ORDER BY emb <=> qv LIMIT 10
-- ❌ 走不了：要先把所有行的距离算出来再排序
ORDER BY 1 - (emb <=> qv) DESC LIMIT 10
```

结果一样，执行路径天差地别。**ORDER BY 里别对距离做运算。**

### 3. `SET LOCAL` 必须和执行语句在同一个事务里

`SET LOCAL` 作用域是当前事务。`SET`（不带 LOCAL）是会话级，**必须同一个连接**。
本单元 `use_index=false` 的写法：

```python
with engine.begin() as c:                    # 开事务
    c.execute(text("SET LOCAL enable_indexscan = off"))
    rows = c.execute(text(sql), params)      # 同一个事务里才生效
```

`/search` 里两条分支都严守这一点，否则开关形同虚设。

### 4. `SET enable_seqscan = off` 是"劝"不是"命令"

小表上 planner 一定选 Seq Scan。想验证"索引确实可用"，只能抬高 seqscan 代价再 `EXPLAIN`。
它只是提高代价估算，连索引都没建时照样 Seq Scan。

## 踩过的坑（真实记录）

1. **连接串**：默认 `postgres:postgres@127.0.0.1` 在本机必然失败，本机是 socket + peer 认证。
2. **`generate_series(:a, :b)` 报 `function is not unique`**：参数被推导成 `smallint`，两个重载都能匹配。必须 `CAST(:a AS int)`。
3. **`:dim::int` 语法错误**：SQLAlchemy `text()` 里 `::` 会被当绑定参数分隔符，用 `CAST(... AS int)`。
4. **不相关子查询只算一次**：早期造数写成标量子查询里的 `random()`，PG 当 InitPlan 只执行一遍，整表同一个向量。改成 `GROUP BY g` 聚合（现在是 numpy 造数 + COPY）。
5. **IVFFlat 建在空表上**：能建成功、不报错，但每次查询只扫一两个随机桶，recall 可能接近 0。`/index` 里加了行数保护。
6. **簇心归一化导致噪声主导**：见上一节，最隐蔽的一个。
