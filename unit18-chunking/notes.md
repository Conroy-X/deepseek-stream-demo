# Unit 18 笔记 · 切块策略

> 切块决定了检索的上限。这一单元的重点不是"写出三种切法"，
> 而是**用数字证明**哪种切法在你的语料上更好。
>
> 状态：29 项自检全过（离线，本地哈希向量）。

## 本次做了什么

- `chunker.py`：`fixed` / `recursive` / `semantic` 三种策略，统一出 `Chunk`
  - `Chunk(id, index, text, start, end, page, strategy)`
  - `coverage()` 用字符掩码算**去重**覆盖率

- `static/index.html`：滑杆调参 + 块列表 + 三策略对比表

## 一、三种策略的本质区别：断在哪

| 策略 | 断开依据 | 代价 |
| --- | --- | --- |
| fixed | 每 `size` 字一刀 | 句子被砍断，答案跨两块 |
| recursive | 段落 → 换行 → 句号 → 分号 → 空格 → 硬切 | 填充率低（块更短更多） |
| semantic | 相邻句相似度低于阈值就断 | 阈值依赖模型，要标定 |

`fixed` 的实现只有四行，但它会在最不该断的地方断：

```python
step = size - overlap          # overlap >= size 时 step <= 0 → 死循环
while i < n:
    piece = text[i : i + size]
    i += step
```

所以 `overlap >= size` 必须直接报错，不能"容忍"。

## 二、递归切分的真实代价（实测）

在 1700 字语料、`size=100、overlap=0` 下：

| 策略 | 块数 | 为什么 |
| --- | ---: | --- |
| fixed | 16 | 每块塞满 100 字 |
| recursive | 20 | 为了在句末断开，每块平均只装 85 字 |

**块数变多不是 bug，是代价**：块更短 → 上下文更碎 → 有时反而更差。
所以"递归一定比固定好"是错的，得看你的语料句子有多长。

## 三、覆盖率必须去重算

有 overlap 时 `sum(len(chunk))` 一定大于原文，看不出有没有丢字。
正确做法是打掩码：

```python
mask = bytearray(total)
for c in chunks:
    for i in range(c.start, c.end):
        mask[i] = 1
sum(mask) / total      # 必须 = 1.0
```

改这个函数之前，递归切法只能到 98.8% —— 因为块被 `strip()` 过，
页与页之间的换行没被任何块覆盖。**差距就藏在那些空白字符里**，
而它们恰好是 Citation 定位偏移的失效点。

## 四、两个真踩到的坑

### 1. 小标题被孤立在块尾

打包时 `费用报销与差旅` 这种 7 字小标题刚好塞得进上一块，于是它挂在
一堆年假条款后面 —— 检索时它谁也不代表。

修法：切分前先「标题粘正文」，并且给正文留出 `size - 标题长度 - 分隔符` 的额度：

```python
head, sep, body = piece.partition("\n\n")
if sep and body and _is_heading(head):
    budget = max(20, size - len(head) - len(sep))
    sub = _atoms(body, budget, rest)
```

第一版忘了减 `len(sep)`，结果出现 101 字的块 —— 只超出 1 个字，最难查。

### 2. 语义切分的阈值不能抄

本单元 49 句、本地哈希向量，相邻句相似度：

```
中位数 0.096 · 最大 0.381
```

| 阈值 | 块数 |
| ---: | ---: |
| 0.05 | 18 |
| 0.10 | 27 |
| 0.30 | 48（≈逐句切） |

阈值 0.3 是网上文章里常见的"经验值"，但那是**真语义模型**的经验值。
本地哈希向量相似度本来就低，照抄 0.3 等于把每句话都切开。
所以默认取 0.05，并在 `notes.md` 里写清楚：换模型必须重新标定。

## 五、固定问题集对比（本单元的核心产出）

`size=160 / overlap=30 / top_k=3`，12 道题：

| 策略 | 块数 | 命中 | recall@3 |
| --- | ---: | ---: | ---: |
| fixed | 10 | 11/12 | 0.92 |
| recursive | 10 | 12/12 | 1.00 |
| semantic | 18 | 12/12 | 1.00 |

fixed 丢的是「退款多久到账」：答案「3–5 个工作日」正好落在两块交界，
两边各带半句，谁都不够像。

> 只有 12 道题的评测集很小，结论只能说明"在这个语料上 recursive 不差"。
> 真实项目要 50 题起步，并覆盖同义改写、跨段组合、无答案（该拒答）三类。

## 一句话总结

切块没有"最佳实践"，只有"在你的语料上验证过的参数"。
块大小影响的是**召回的上限**，而验证它只需要一件事：一小组带标准答案的问题。

## 面试追问

1. **「chunk_size 怎么定？」**
   → 先看答案的平均长度：答案通常 100–300 字，块就该比它略大（300–500 字），
   保证一块能装下完整答案。再用固定问题集扫 200/400/800 三档，选 recall 最高且成本可接受的那档。
   不要抄"512 token"，那是英文语料的经验。

2. **「overlap 要设多少？」**
   → 典型是 size 的 10%–20%。overlap 的作用是防止答案被切断，
   代价是索引膨胀（存两遍）和检索结果重复。如果块本身就在句子边界断开，overlap 可以设 0。

3. **「语义切分比递归好吗？」**
   → 不一定。语义切分要算 N 次 embedding（成本高），阈值还要标定，
   而递归在大多数结构化文档（有标题、有段落）上已经够好。
   结构化文档优先用「按标题层级切」，那才是真的语义边界。

4. **「怎么评估切块好坏？」**
   → 端到端看 recall@k 和答案正确率，别单独评"块是否连贯"。
   因为块漂亮但召回差，对你的产品毫无意义。
