## 一、先把「问题」分级，再谈渲染

`validate_answer_payload()` 返回的是 `[{level, code, message}]`，不是 `bool`。

```
error   → 缺字段 / 重复 id / id 非正整数 / page 非法 / 协议不在白名单 / 超长
warning → 未知 [9] / 有引用没人用 / 后端标了 incomplete
```

为什么必须两级：只要是一个 bool，前端就只剩「渲染 / 不渲染」两个动作，
于是「这份响应能用，但其中有个角标是坏的」这种情况**无处表达**，只能整页白屏。
分成两级之后，warning 照常渲染并把角标标红，error 才拦。

实测四份 fixture：

| fixture | 问题码 | renderable |
| --- | --- | --- |
| `normal` | — | ✅ |
| `missing_page` | —（不是问题，是能力缺失） | ✅ |
| `unknown_marker` | `UNKNOWN_MARKER` warning | ✅ |
| `malicious` | `BAD_URL` + `DUP_ID` error | ❌ |

注意 `missing_page` 一个问题码都没有 —— 它**不是错误**。把「数据没页码」当成校验失败，
是这一章最容易走偏的地方。

## 二、`isinstance(True, int)` 是 `True`

Python 里 `bool` 是 `int` 的子类。所以 JSON 里的 `"id": true` 会顺利通过
`isinstance(cid, int) and cid >= 1`，被当成 `1`，然后和正文里真正的 `[1]` 撞车，
渲染出来两个角标指向同一条引用，还没有任何报错。

```python
if isinstance(cid, bool) or not isinstance(cid, int) or cid < 1:
    → BAD_ID
```

自检里专门有一条 `id=True 也被拦下（bool 是 int 的子类，别漏）`。
同类问题还有 `page`：`"page": true` 一样能混进来。

## 三、跳转是可选能力，不是必然能力

`jump_target()` 只有三种返回：

| status | 条件 | UI 该怎么画 |
| --- | --- | --- |
| `ok` | 有 page、协议合法 | 给「打开第 N 页」按钮，附 `#page=N` |
| `no_page` | 有原文、没页码 | 展开片段 + 说明「这条来源没有页码」，**不给按钮** |
| `bad_url` | 协议不在白名单 | 禁用，连「复制链接」都不给 |

三条实现上的决定：

1. `no_page` 时**不返回 `url` 字段**。前端拿不到链接，就不可能「顺手」拼一个跳到第 1 页的假链接。
   能力缺失要在数据层就表达出来，不能指望每个调用方都记得判断。
2. 用 `url#page=N` 而不是自己算滚动位置。`#page=` 是 PDF 阅读器的原生锚点，
   缩放、换设备、换阅读器都稳；自己算 offset 的版本在别人机器上必错。
3. `bad_url` 是 error 级，`no_page` 不是 warning。前者是数据坏了，后者是数据本来就这样。

## 四、渲染：一条出口，先转义

```python
safe = html.escape(answer, quote=True)   # 先
MARKER_RE.sub(repl, safe)                # 后
```

`malicious` fixture 里答案开头是 `<img src=x onerror=alert(1)>`，渲染出来必须是
`&lt;img src=x onerror=alert(1)&gt;` —— **onerror 作为文本留在页面上是无害的**，
有害的是它作为属性被解析。

所以自检的判据不是「字符串里有没有 `onerror`」（那样永远为真、测了个寂寞），
而是：把所有自家生成的 `<sup …>` 标签剥掉之后，剩下的部分**一个 `<` 都不能有**。

```python
rest = re.sub(r"</?sup\b[^>]*>", "", hm)
assert "<" not in rest
```

引用侧栏的片段也一样：`render_citation_text()` 单独 `html.escape` 一次。
大家写这类页面时只想着转义答案，很容易漏掉侧栏里的文档原文 —— 它同样来自不可信文档。

## 五、竞态：连点三个角标，谁上屏

真实场景：用户点 `[1]`，网卡，又点 `[3]`，再点 `[5]`。三个请求同时在飞。
如果按「先到先渲染」，最后上屏的可能是 `[1]` 的内容，而角标高亮着 `[5]`。
这种 bug 只在网络抖动时出现，没有日志根本查不出来。

```python
class RaceGuard:
    def begin(self):  self._seq += 1; return self._seq
    def accept(self, t): return t == self._seq
```

页面上是同一个逻辑：点击时 `++seq` 拿 token，`await` 回来后 `token !== seq` 就丢弃并计数。
实验台里点「连点 [1][2][3]」能看到「丢弃过期响应 N 次」上涨，日志里写着哪一条晚到了。

注意这里有个反直觉的点：**丢弃不是失败**。丢弃的响应本来就不该显示，
所以界面不该有任何报错，只有一行内部计数。

## 六、页内定位失败也要给东西

`locate_in_page()` 找不到片段时返回 `found: false`，接口仍然返回整页文本，
只是带上 `degraded: true`。

理由很实际：定位失败的原因通常是「原文改了」或「片段被截断」，
用户此刻的需求是「让我看看这页」，而不是「告诉我定位失败」。
给他整页，他自己扫一眼就能找到；只给一句错误，他还得再点一次「打开原文」。

## 一句话总结

**引用 UI 的难点不在画角标，而在把「没数据 / 没页码 / 链接有毒 / 请求来晚了」这四种情况分别画对。**

## 面试追问

**Q：为什么不用 `dangerouslySetInnerHTML` 的等价物直接塞 Markdown 渲染结果？**
A：那等于把「转义」这一步交给了渲染器的默认配置，而默认配置经常允许内联 HTML。
本单元只支持一种标记（`[n]`），所以自己写 15 行 `escape + sub` 比引入一个 Markdown 渲染器
再配置 sanitizer 更可控，也更容易证明它是安全的 —— 安全边界越窄越好证明。

**Q：竞态守卫为什么放在前端而不是后端？**
A：后端不知道用户又点了一次。它每次请求都是独立合法的，丢掉任何一次都是错的。
只有发起方知道「我已经不关心上一个响应了」，所以 token 必须由前端持有。
后端能做的是让响应可被取消（连接断开就停止生成，Unit 27 做过）。

**Q：`no_page` 这种情况，产品上还能做点什么？**
A：两件事：一是把片段展开、允许复制；二是**在入库时就补页码**。
来源是 PDF 就记页，是 Markdown 就记章节锚点，是网页就记段落序号 ——
`page` 字段不应该允许长期为空。UI 的降级是兜底，不是常态。

**Q：如果引用数量上千，前端渲染会不会卡？**
A：会。`[n]` → `sup` 的替换是线性的，但每个 `sup` 都挂监听、每份引用都建 DOM 节点，量大了就明显。
生产做法是事件委托（在容器上挂一个 click，从 `event.target.dataset.n` 取值），
引用列表用虚拟滚动或分页。本单元为了可读性用了逐个绑定，注释里没说，但这是已知的取舍。
