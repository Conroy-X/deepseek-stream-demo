## 一、余弦相似度：手算一遍就再也不会忘

$$\cos(a,b) = \frac{a \cdot b}{|a|\,|b|}$$

拿二维举例：`a = (1, 0)`，`b = (1, 1)`

```
a·b  = 1×1 + 0×1 = 1
|a|  = 1
|b|  = √2 ≈ 1.4142
cos  = 1 / 1.4142 ≈ 0.7071      ← 相当于夹角 45°
```

取值范围 `[-1, 1]`：

| cos | 含义 |
| --- | --- |
| 1 | 方向完全一致 |
| 0 | 正交，完全无关 |
| -1 | 方向完全相反 |

### 为什么用余弦，不用欧氏距离

余弦只看**方向**，不看长度。一段话和它自己复制三遍：

- 方向完全相同 → 余弦 = 1
- 欧氏距离却很大（因为向量变长了）

文本检索关心的是"讲的是不是同一件事"，不是"写得多长"。所以用余弦。

### 为什么先做 L2 归一化

归一化后 `|a| = |b| = 1`，于是：

$$\cos(a,b) = a \cdot b$$

少算两次开方和一次除法。**几乎所有向量库（pgvector、Milvus、Qdrant）都要求入库前归一化**，
原因就是这个 —— 内积直接当余弦用，快得多。所以代码里 `l2_normalize` 在 `embed` 内部就做掉了。

## 二、向量为什么能表达语义（真 embedding）

模型在大量文本上训练时学到的是"什么样的上下文会一起出现"。
"汽车"和"轿车"出现在相似的上下文里（都在讲交通工具、价格、油耗、上路），
于是它们被推到相近的方向上。

所以关键不是"向量"这个容器，而是**模型在里面编码了语料的共现规律**。
换成哈希向量（本单元 local 后端），同样的容器里装的只是字面统计，语义信息为零。

## 三、实测：本地哈希向量有多弱（本单元最重要的数据）

| 对比 | 本地哈希后端 | 真语义模型（预期） |
| --- | --- | --- |
| 「汽车」vs「轿车」 | **0.000** | 0.8+ |
| 「API」vs「FastAPI」 | **0.000** | 0.4+ |

## 四、三个实现细节（都是坑）

### 1. 哈希必须用 blake2b，不能用内置 `hash()`

```python
hashlib.blake2b(token.encode(), digest_size=8)   # ✅ 跨进程稳定
hash("汽车")                                      # ❌ 每个进程不一样！
```

Python 对 str 的内置 `hash()` 加了**随机盐**（PYTHONHASHSEED），
换个进程结果就变。用它的后果是：写进库的向量和查询时算出来的向量对不上，
检索结果永远错乱，而且**重启服务后表现还不一样**，极难排查。

### 2. 中文必须切 bigram

中文没有空格，按单字切会把"上海"和"海上"混成一堆，语义信息几乎归零。
bigram（相邻两个字）能天然带住词边界，是低成本分词的标准做法
（Elasticsearch 的 CJKAnalyzer 就是这么干的）。
真要做到好，需要 jieba 或模型自带的 tokenizer。

### 3. sublinear tf 加权

```python
weight = 1.0 + math.log(cnt)
```

出现 100 次的词不该比出现 1 次的重要 100 倍。取对数把差距压下来，是 TF-IDF 里的标准做法。

## 五、暴力检索到底行不行

```python
scores = [cosine(q, d) for d in docs]     # O(N·d)
top_k = sorted(scores)[-k:]
```

这叫 **flat / brute-force** 检索。N 在几千、几万以内，它**比任何向量库都快**——
因为省掉了索引构建、网络往返、序列化开销。

所以"要不要上向量库"的第一个判断标准是**数据量**，不是"别人都在用"。
数据量上来（十万级以上）才需要 HNSW / IVFFlat 这类近似最近邻（ANN）索引，
那是 Unit 16 的事。

一句话：**先 flat，跑不动再上索引。** 提前上向量库只会增加运维复杂度。

## 一句话总结

Embedding 把"意思"变成一个方向，余弦相似度就是两个方向的夹角；
但方向里装的是语义还是字面，完全取决于**用哪个模型算的**——
自己哈希出来的只装字面，这就是为什么 RAG 里模型选型比算法更重要。

## 面试追问

1. **「为什么用余弦不用欧氏距离？」**
   → 余弦只看方向不看长度，对文本长度不敏感（长文档和它的摘要方向一致）。
   归一化之后两者单调等价，但余弦有明确上界 1，好设阈值。

2. **「向量维度越高越好吗？」**
   → 不是。维度高表达力强，但内存和检索成本线性上升，且边际收益递减
   （bge-m3 是 1024 维，text-embedding-3-small 是 1536 维，都很够用）。
   维度还必须和入库时一致 —— 换模型必须重建整个索引，这是最常被忽略的迁移成本。

3. **「怎么判断 embedding 模型好不好？」**
   → 不用看榜单，用你自己的数据做**检索命中率**测试：准备 50 组「问题 + 应召回的原文」，
   算 Recall@5 / MRR。榜单（MTEB）只能参考，中文业务场景差异很大。

4. **「同一个模型，中英文能互搜吗？」**
   → 多语言模型（bge-m3、text-embedding-3）可以，但效果弱于同语言。
   跨语言检索要么用多语言模型，要么先翻译再搜。

5. **「为什么不能换模型后直接用老向量？」**
   → 不同模型的向量空间完全不同，连维度都可能不一样。
   A 模型生成的向量在 B 模型的空间里毫无意义。换模型 = 全量重建索引。

6. **「余弦相似度多少算相关？」**
   → 没有通用阈值。同一模型下 0.7 可能相关，换了模型 0.7 可能全是噪声。
   必须用你的数据统计可疑样本，画分数分布来定。硬编码 0.8 是新手的经典错误。
