# Unit 36 笔记 · 工具坏掉的时候，循环不能跟着坏

> 异常、超时、死循环、重复调用 —— 这四件事在 demo 里都不会发生，在生产里每天都会发生。

## 本次做了什么

- `resilience.py`：`call_tool()`（异常/超时统一成 `ToolResult`）、`call_many()`（并行且互不牵连）、`LoopBreaker`（同参第 N 次熔断）、`IdempotencyStore`（按 key 只执行一次）、带四道防线的 `run_agent()`。
- `main.py`：`World`（故障在这里注入）、`OfflineModel` / `LoopModel`、`/fault` 故障注入接口、49 条自检。
- `static/index.html`：五个注入按钮、trace 时间线、熔断原因、幂等对照表。

## 一、异常：翻译成消息，而不是往上抛

```python
except Exception as e:
    return ToolResult(name, False, "exception", error_content("exception", f"{type(e).__name__}: {e}"))
```

关键是 `kind` 字段。有了它，同一句「工具失败了」在日志里能分成 `exception` / `timeout` / `blocked` / `unknown_tool` / `bad_arguments` 五类，排障时不需要翻代码猜是哪种。实测异常场景墙钟 **0.1ms**，答案是「工具失败（exception）：RuntimeError: 行情服务 500 Internal Error。」—— 用户看到的是原因，不是 500。

## 二、超时：`wait_for` 只取消它自己

工具要睡 3 秒，预算 0.5 秒，实测墙钟 **500.8ms**。省下的 2.5 秒就是 `asyncio.wait_for` 的全部价值。

它比 `asyncio.timeout()` 的整段超时更精准的地方在于：取消的是**那一个协程**，同批其他调用不受影响。自检里三个并发调用全部走超时路径，实测 1.5 秒内全部返回 —— 如果是串行执行，光等待就是 9 秒。

代价是：被取消的协程可能停在任意位置。真实工具如果在 `await` 之间改了共享状态，超时会留下半个副作用。所以**有副作用的工具必须自带事务或幂等**，不能指望超时帮你擦屁股。

## 三、熔断：检查放在执行之前

```python
reason = breaker.hit(name, args)      # 先问
if reason: block()                    # 再决定执行不执行
results = await call_many(...)         # 最后才执行
```

顺序反过来就是灾难：第 3 次重复调用先执行再判断，退款就已经退第二次了。
实测死循环场景 `tool_calls_executed == 2`（不是 3），就是这条顺序的直接证据。

键用 `name + json.dumps(args, sort_keys=True)`。`sort_keys` 不是洁癖：
`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 是同一个调用，不排序就会被当成两个不同的调用，熔断永远不触发。

熔断时还有一个 Unit 33 留下的债要还：assistant 那条消息里已经写了 `tool_calls`，
直接 break 会让 messages 变成「有请求没应答」的非法态。所以补一条
`{"kind": "blocked", "message": "重复调用已被熔断，未执行"}` 的 tool 消息。自检里断言
`len(tool_msgs) == len(calls)`。

## 四、幂等：重试和幂等是两件事

```
第一次  call_fixed_001 → 真的执行，effect_no=1
第二次  call_fixed_001 → replayed=True，effect_no=1   ← 没有真的退第二次
第三次  call_fixed_002 → 真的执行，effect_no=2
```

`IdempotencyStore.once(key, fn)` 三行逻辑：命中缓存就返回 `(缓存, True)`，没命中才 `await fn()`。
实测同一个 key 调两次，`replays == 1`、`effect_count_after_replay == 1`。

为什么必须用 `tool_call_id` 做 key：用户可能真的想买两次一样的东西，
「参数相同」不等于「同一件事」。而没有 id 的场景（定时任务）只能用业务键，
那时「两次相同请求」就无法区分 —— 这是取舍，要写进文档，不能装作不存在。

## 五、正常路径一个字都没改

新增四道防线最容易出的事故是：把正常路径也改慢了、改错了。所以自检里专门有
「正常路径出答案 2 步、无熔断事件」，以及页面上的「正常」按钮 —— 行为和 Unit 34 完全一致：
`model → tool(ok) → model`，墙钟 10.4ms（就是工具里那个 `sleep(0.01)`）。

工程上的说法：**降级逻辑必须和正常逻辑共享同一条主路径**，只在分支上加保护。如果为了「容错」写了一整套平行实现，那你就有两份需要维护的循环 —— 而只有一份会被真正跑。

## 完成标准对照

| 标准 | 达成情况 |
| --- | --- |
| 异常 → `ToolResult(ok=False)` | `kind=exception`，0.1ms 返回，调用方不捕获异常 |
| 超时不阻塞循环 | 预算 0.5s、工具睡 3s，墙钟 500.8ms；并发三个也不串行 |
| 死循环熔断 | 同参第 3 次触发，`stopped=loop_detected`，工具只执行 2 次 |
| 幂等去重 | 同 key 副作用 1 次、`replays=1`；换 key 才 2 次 |
| 熔断写进 trace | `type=breaker` 条目 + `breaker_events[].reason` |
| 正常路径不受影响 | 2 步出答案、无熔断事件、墙钟 10.4ms |

## 一句话总结

**容错不是「让工具不失败」，是「让失败变成一个模型能读懂、你能定位的事件」。**

## 面试追问

**Q：超时时间设多少？**
A：按 P99 的 2~3 倍设，不是按平均。本单元工具是本地计算所以 0.5s 够；真实 HTTP 工具一般 5~10s。更重要的是**分层**：单次工具超时 < 单步总超时 < 整个请求超时，否则内层永远等不到外层的兜底。如果供应商的 P99 是 8s，你设 3s 会让 5% 的正常请求变成超时 —— 那不是容错，是自残。

**Q：熔断的阈值为什么是 3 次，不是 5 次或 10 次？**
A：这是「合法重复」和「死循环」的分界线。合法的 Agent 很少对同一工具用完全相同的参数连调 3 次（第二次就该换参数或换工具了）。设太大（10 次）意味着白白多花 7 步的钱和时间；设太小（2 次）会把「重试一次」这种正常行为误杀。3 是本单元的选择，真实系统要按业务调，但**必须显式设定**。

**Q：幂等键用 tool_call_id 有什么问题？**
A：模型每次生成的都是新 id，所以「同一次用户请求重试」能识别，但「用户点了两次退款」识别不了 —— 那是两个不同的请求，本来就该退两次（或者由业务层拦）。真正的陷阱是：如果客户端在超时后**重新生成**了 tool_call_id（有些 SDK 会），幂等就失效了。所以幂等键经常要用 `tool_call_id + 业务键` 做联合约束，让数据库兜底，而不是靠内存里的字典（进程重启就没了）。

**Q：为什么不直接用 tenacity / 重试库把失败都重试一遍？**
A：因为有些失败重试是有害的。参数错（`bad_arguments`）重试一万次还是错；超时重试可能让已经成功的操作执行第二次；熔断触发后重试等于死循环。本单元的四类 `kind` 其实就是在回答「该不该重试」：`exception` 可能值得重试一次，`timeout` 只有在工具幂等时才值得重试，`bad_arguments` 和 `blocked` 绝对不能重试。盲目重试是把错误放大，不是容错。
