## 渲染 Markdown 的 6 个坑

### 1. 顺序：先转义，再替换

```
❌ 先替换 **粗体** 再 escapeHtml → XSS 风险
✅ 先 escapeHtml，再替换
```

### 2. 行内代码要提前「占位」

`**` 如果出现在 `` `code` `` 里，不能被当成加粗。
做法：先把行内代码抠出来存成占位符，最后再还原。

### 3. 链接只允许 http/https

```javascript
/\[([^\]]+)\]\((https?:\/\/[^\s)]+)\)/g
```
不加限制的话 `[点我](javascript:alert(1))` 就是 XSS。

### 4. 代码块用状态机，不用正则

```javascript
if (fence) inCode = !inCode;      // 遇到 ``` 翻转
if (inCode) { codeBuf.push(line); continue; }  // 代码块内不解析任何 Markdown
```

### 5. 未闭合的代码块不能丢

流式输出到一半，```` ```python ```` 后面的内容可能还没到。
如果丢弃，用户会看到内容凭空消失。

### 6. 复制按钮用事件委托

消息是动态插入的，逐个绑事件会内存泄漏。
在父容器绑一次，用 `e.target.closest(".copy-btn")`。

## 流式渲染的性能

逐字符 `innerHTML = renderMarkdown(raw)` 会很卡。

当前做法：
- 每收到 delta 就重渲染整段（简单、可靠）
- 用 `requestAnimationFrame` 节流滚动

优化方向（以后）：
- 只在「结构性 token」到达时重渲染（`\n`、```` ``` ````、`|`）
- 或改用 diff 更新

## 我自己的话解释「为什么不能用正则解析 Markdown」

**正则只认字符，Markdown 要认状态。** 同一个 `*`，在正文里是斜体、在 `` `code` `` 里是字面量、
在 ```` ``` ```` 围栏里整段都不该被解析 —— 正则看不到这层「我现在在哪一层」的上下文，
只能一行一行硬匹配。具体会挨三刀：

1. **块级结构是有优先级的**。`# 标题` 出现在代码块里就不是标题；引用里嵌列表、列表里嵌代码块，
   正则得靠回溯去猜层次，写着写着就快变成自己实现一个解析器了。
2. **同一行里语法会互相吞**。`**` 落在行内代码里不能被加粗 —— 这正是本单元要把行内代码
   「抠成占位符」的原因。正则没有「先挖走、再放回」的概念，只能靠人工加补丁。
3. **流式输入本身就是半截的**。模型还在吐，```` ``` ```` 可能只到了一半。正则面对不匹配的输入
   只能「整段不处理」，表现就是内容凭空消失；状态机则能「遇到 ```` ``` ```` 翻转 `inCode`，
   没闭合就一直当代码块」，把半截内容先渲染出来。

所以本单元的分工是：**块级用状态机（按行扫、维护 `inCode` 和当前块类型），行内才用正则。**
行内语法本来就局限在一行内、没有嵌套优先级，正则够用；一旦需要跨行判断，就必须换状态。

## 一句话总结

**Chat UI 的难点从来不是「把 Markdown 渲染出来」，而是两件事：一是安全**（先转义再替换、链接只放
http/https、模型给的原始 HTML 一律不执行）**；二是「输入永远是半截的」**（流式下要能容忍未闭合
的代码块、不因解析失败丢内容，还得每帧重渲染 + 节流滚动才不卡）。

## 面试追问

1. **「前端渲染 Markdown 有什么安全风险？」**
   → XSS。必须转义原始 HTML，限制链接协议，代码高亮库也要注意别引入 `dangerouslySetInnerHTML` 的漏洞。

2. **「流式渲染 Markdown 有什么难点？」**
   → 内容不完整。可能收到半个代码块、半个表格。要能容忍「未闭合」状态，
   并且不能因为解析失败就丢内容。

3. **「怎么做代码高亮？」**
   → 生产用 Shiki / highlight.js / Prism。本单元为了零依赖手写了一个极简词法高亮，
   只识别关键字/字符串/数字/注释/函数名。
