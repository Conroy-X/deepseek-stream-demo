# Unit 35 笔记 · 工具变多之后，问题是选哪个

> 执行代码一行没改，准确率从 1.00 掉到 0.60 —— 变的只是工具描述。

## 本次做了什么

- `routing.py`：5 个工具（天气/计算/汇率/单位/订单）+ 词面路由器（1~3 字 n-gram 交集 + IDF 加权）+ 10 道固定题 + 三档劣化配置（`vague_tools` / `bare_tools` / `TOOLS_2`）。
- `main.py`：`OfflineModel`（路由 + 正则抽参数）、`plan()`（两个城市就发两个调用）、`execute_calls()`（独立 try，一个坏不影响另一个）、5 个接口、51 条自检。
- `static/index.html`：工具清单、命中片段高亮、并行结果、四档准确率对照表。

## 一、路由器的实现：故意用最笨的办法

```python
def ngrams(text):                 # 中文切 1~3 字片段，英文按 token
def rank(question, tools):        # 对每个工具算 Σ idf(f) × len(f)**1.3，f 是跟问题共有的片段
```

没有向量、没有模型，好处是**确定性**：同一个问题永远得到同一个分数，才谈得上测准确率。
IDF 让「多少」「是」这种到处都有的片段权重变低，「公里」「汇率」「SO」这种只出现在个别工具里的权重变高。
`len(f)**1.3` 让三字片段（「人民币」）压过单字（「币」）。

实测分数很有区分度：`5 公里是多少米` → `convert_unit` 7.572，`convert_currency` 0（一个共同片段都没有）。
而 `把 180 磅换算成公斤` → `convert_unit` 20.338 vs `convert_currency` 15.539 —— 只差 4.8，
因为「换算」同时出现在两个工具的枚举和描述里。**这一个数字就是「描述没写清区分点」的量化证据。**

## 二、三档描述，三个准确率

| 配置 | 命中 | 具体丢了什么 |
| --- | ---: | --- |
| 描述完整 | 10/10 | — |
| 描述含糊（「处理换算相关的请求」） | 9/10 | `SO-000456 现在什么状态` 分数 0 |
| 删掉 description | 6/10 | 计算 2 题、订单 2 题全丢 |
| 只有两个工具（天气+计算） | 4/10 | 3 类能力缺失，4 题被硬塞给天气 |

注意「含糊」只掉了 1 题：因为 `处理天气相关的请求` 里「天气」「订单」这些词还在，
路由器仍然能接住。真正致命的是**完全删掉** —— 中文问题跟英文工具名一点交集都没有，
`ngrams("get weather")` 里没有任何汉字。这一步掉 4 题。

结论不是「描述要长」，而是「描述里必须包含用户会说的词」。`处理订单相关的请求` 比不上
`按订单号查询物流状态和金额`，因为后者多了「订单号」「物流」「状态」「金额」四个真实用户会说的词。

## 三、最危险的误选：把问题塞给「最像」的工具

```
Q: 深圳到北京的机票多少钱
→ get_weather  分数 12.66（第二名 convert_currency 只有 0.288）
```

理由很直白：五个工具里只有 `get_weather` 的枚举写着「深圳」「北京」，两个字都把分数拉满。
后果不是报错，是产出**一个用天气回答机票问题的答案** —— 用户看到的是一段通顺但完全无关的话。

这条被写成了断言（`picked == "get_weather"`），没有从题集里删掉。同时验证了设计原则：
`route()` 在所有分数都是 0 时返回 `None`，而不是「挑一个最高的」。
选不出来是安全的（模型会说「我没有这个工具」），选错是危险的（模型会编）。

## 四、并行调用：形状对了，性能是次要的

「上海和北京今天多少度」→ `plan()` 直接发两个 `get_weather` 调用，`execute_calls()` 各自计时，
按 `tool_calls` 顺序回填两条 tool 消息。实测单次工具 0.0~0.1 ms，并行在这里毫无性能收益。

那为什么还要做并行？因为**形状**：一个 assistant 消息对应 N 条 tool 消息，少一条就是 400。
真工具（HTTP 请求、数据库查询）才是 50~500ms 级别，那时 `asyncio.gather` 才有意义 ——
但形状不变，所以先在小工具上把形状做对，比先做并发划算。

回填顺序必须跟 `tool_calls` 一致，不能跟完成顺序一致。本单元串行执行所以两者相等，
真并行时完成顺序随机，这一条就会变成一个很难查的 bug（日志里 id 和参数对不上，看起来像模型传错了参数）。

## 五、参数抽取是离线模型的「手」，不是重点但会毁掉演示

`fill_args()` 用正则从问题里抠：城市取枚举里出现的第一个、订单号匹配 `SO-\d{6}`、
货币/单位**按在问题里出现的先后排序**（`sorted(..., key=question.index)`）。

最后这一点踩过：`{"100 美元能换多少人民币"}` 一开始取到了 `from=人民币, to=美元`，
因为遍历的是 `RATES` 字典（`人民币` 在前）。方向反了结果就从 710 变成 14.08 —— 数字看着还挺合理，
所以这类 bug 只能靠断言（`from_currency == "美元"`）抓。

## 完成标准对照

| 标准 | 达成情况 |
| --- | --- |
| 5 个工具各自能被路由到 | 10 道题逐条断言，10/10 |
| 并行多调用并按 id 回填 | 2 个、3 个调用各一条断言，`call_id` 与 `tool_calls` 顺序一致 |
| 误选被记录 | 「机票」→ `get_weather` 分数 12.66，写成断言；两工具配置下「美元」→ 天气也有断言 |
| 描述缺失导致失败 | 删描述后 6/10，四题分数为 0，逐条断言 |
| 准确率随工具数/描述变化 | 10 / 9 / 6 / 4 四档，同一批题 |
| 一个工具坏不影响别的 | 「杭州失败 + 北京成功」两个调用都回填 |

## 一句话总结

**工具的可发现性完全由描述决定 —— 你没写进 description 的词，模型和路由器都看不见。**

## 面试追问

**Q：真实项目里为什么不用这种词面路由，而用模型自己选？**
A：规模小的时候模型选得好（它读得懂「帮我看看明天用不用带伞」），但工具过了二三十个，选错的概率会明显上升，而且每次都要把全部 schema 塞进上下文（Unit 32 算过：20 个工具十几 KB）。常见做法是两段式：先用一个便宜的检索/分类器把候选从 30 缩到 5，再让模型在这 5 个里选。本单元的词面路由器就是那个「便宜的第一段」的最小实现。

**Q：怎么衡量路由质量？只看准确率够吗？**
A：不够。至少要分开看三种错：**选错**（选了个不该选的，会产出跑偏的答案）、**选不出**（分数全 0，模型会说不知道）、**该多选却单选**（用户问了两件事，只调了一个工具）。本单元的 `/bench` 只统计了第一种和第二种的合并数，多选的情况是用 `plan()` 单独测的。真实系统还要加上延迟和成本 —— 路由本身也是一次模型调用的话，它就在给每条请求加钱。

**Q：工具描述写多长合适？**
A：写到「能覆盖用户会用的词」为止，不是越长越好。本单元 5 个工具的描述都在 30~45 字，刚好覆盖了 10 道题用到的词。写太长的两个代价：每轮都占 token（Unit 32 算过），以及词面覆盖太广反而抢别人的问题（「换算」出现在货币和单位两个工具里，就是本单元实测的那个 4.8 分差距）。判断标准很实际：拿 20 条真实用户问题跑一遍，看有没有分数接近的候选对。

**Q：模型一次返回多个 tool_calls，要不要都执行？**
A：看工具是否有副作用。只读工具（查询、换算）可以全执行；有副作用的工具（退款、下单）要先做幂等检查（Unit 36 会讲），或者干脆改成串行、让模型看到第一个结果再决定第二个。本研究里 3 个 `get_weather` 并行没有风险，但换成 3 个 `refund_order` 就必须先问「这三个 id 是不是同一笔」。
