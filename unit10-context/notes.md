## 为什么会撑爆

LLM 无状态，每轮重发完整历史。实测（每条约 100 字）：

| 轮次 | 本次输入 token |
| --- | --- |
| 1 | 155 |
| 5 | 747 |
| 10 | 1487 |

- 第 10 轮的输入是第 1 轮的 **9.6 倍**
- 10 轮累计约 **8,210** tokens
- 32 轮左右就会超出很多模型的窗口

**四个后果**：超窗口报错 / 变贵 / 变慢 / 变傻（lost in the middle）

## 三种策略对比（实测，预算 600）

| 策略 | 最终 token | 丢弃 | 省下 | 代价 |
| --- | --- | --- | --- | --- |
| none | 1487 | 0 | 0% | 会报错 |
| sliding | 599 | 12 | 59.7% | **彻底失忆** |
| summarize | 329 | 16 | 77.9% | 多一次模型调用 + 摘要可能失真 |

### 各自的保护机制

- **sliding 的 `min_keep=2`**：哪怕超预算也保留最近 2 条。
  宁可贵一点，也不能把用户刚说的话丢掉。
- **summarize 的 `keep_recent=4`**：最近几轮**原样保留**不摘要。
  因为最近的对话有指代关系（「它」「那个方案」指什么），压成摘要就丢了。

## 上下文预算表（面试必背）

```
上下文预算表
----------------------------------
上下文窗口总量         64,000  100.0%
预留输出               4,096    6.4%
System Prompt            300    0.5%
用户本轮输入             200    0.3%
检索片段(RAG)              0    0.0%
可用于历史            59,404   92.8%
```

**核心原则：先扣掉「预留输出」，剩下的才是历史的预算。**
反过来会经常出现回答被截断（`finish_reason='length'`）。

## token 估算的误差

本单元用公式估算，不是精确计数：

```python
cjk / 1.5 + other / 4   + 4*条数
```

误差来源：
- 没有 tiktoken（要联网下词表，本机 GitHub 不通）
- DeepSeek / GPT 的词表不同
- 每条消息的格式开销按 4 估

**建议**：做预算分配 ±20% 完全够用；要精确对账就用 API 返回的 `usage.prompt_tokens`。

## 面试追问

**Q: 为什么摘要用 keep_recent=4 而不是全部摘要？**
> 最近几轮的细节对当前回答最关键。压成摘要会丢失指代关系
> （「它」「那个方案」到底指什么）。摘要只适合处理「已经结束的话题」。

**Q: 摘要什么时候触发？**
> 按 **token 超预算**触发，不是按轮数。每条消息长度差异很大，
> 按轮数会误判（10 条短消息可能还没 1 条长消息占得多）。

**Q: 摘要压缩会省钱吗？**
> 不一定。每次摘要本身就是一次模型调用（有成本有延迟）。
> 只有当「省下的输入 token 成本 > 摘要调用成本」时才划算。
> 实践上：长对话（>20 轮）划算，短对话用 sliding 更经济。

**Q: lost in the middle 是什么？**
> 模型对长上下文**中间位置**的信息利用率低于开头和结尾。
> 所以重要的上下文应该放在开头（System）或最近（末尾），中间的可以牺牲。
